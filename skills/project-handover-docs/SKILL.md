# 项目交接文档包生成

## 何时用

用户要把一个**进行中的项目/需求**交给别人接手，需要：
- 说明已完成什么、当前进度、待办与优先级
- 横向对比多个并列场景/任务
- 索引已有资料的出处与用途
- 补充接手人需要的背景信息

## 铁律：先实测，后撰写

**既有文档与项目台账中的"已完成""已落地"表述不可信**。交接文档的价值恰恰在于校正它们。

动手写任何内容前，必须实测：

| 实测对象 | 方法 | 能发现什么 |
|---|---|---|
| 文档声称改过的**代码** | `grep -rn "<关键标识符>" --include="*.java" --include="*.js" --include="*.vue" .`（排除 node_modules） | 文档说"已补 X 映射"但全仓 0 命中 → 功能性缺陷 |
| 文档声称新增的**方法/常量** | `grep -rn "<方法名>\|<常量名>" <源码目录>` | 方案写得很完整但代码一行没动 |
| 文档声称已入库的**配置** | 找数据库导出 dump（Navicat `.txt`/`.sql`），`grep INSERT INTO` 看实际内容与时间戳 | 配置与文档口径不一致（如占位符大小写） |
| **台账口径** | 读 `agent_memory/requirements.md`、`progress.md` | 台账停留在旧版方案（如"拆四环节"已被"两字段对比"取代） |
| **契约闭合性** | 把 SQL 里的绑定参数（`:X`）与前端实际传的键名对账 | 绑定参数无人提供 → 静默失效 |

> **静默失效**是最值得挖的一类缺口：不报错、不生效，只有把"SQL 绑定的参数名"和"前端实际 payload 的键名"逐一对账才能发现。

## 规模裁剪（先问，再写）

**默认不要一上来就写 6 个文档**。交接包的体量必须匹配项目复杂度与用户偏好。

| 情况 | 输出 |
|---|---|
| 只有 1~2 个已完成的场景 + 若干待做 | **1 个文档**：`进度.md`（已完成 + 当前状态 + 待做 + 环境约束 + 资料位置） |
| 多场景且都已开工、接手人要接手编码 | 3~4 个：进度 + 对比 + 资料索引（+ 风险缺口） |
| 大型项目、跨团队交接 | 6 个：本节的完整结构 |

**判断依据**：未开工的场景**不要**铺开写设计细节（那属于方案文档的职责），交接文档里只写"待做 + 待确认项 + 已备资料在哪"即可。

若不确定体量，**先问用户要"一份简单的进度说明"还是"完整交接包"**，不要默认输出完整包。

## 完整结构（仅在需要时使用）

目录名建议：`docs/<需求目录>/交接文档/`

### `README.md` — 交接入口
1. **一句话结论表**：每场景一行 = 状态 + "接手人第一步该做什么"
2. **接手优先级建议 + 理由**（不要只排序，要说清为什么）
3. **5 分钟速览**：用一张表讲清"三者最关键的区别"
4. **文档导航表**：顺序 / 文档 / 内容 / 什么时候看
5. **原始文档在哪**（交接目录是视图，不替代方案文档）
6. **开工前硬约束**（环境限制、禁忌操作）
7. **🔴 需立即知悉的实测缺口**（把最危险的放最前，标注严重度）

### `01-背景与架构.md` — 动手前必读
- 项目是什么、涉及哪些子系统、哪些要改哪些不改
- **执行链路图**（从入口到落库/展示的完整调用链）
- 改动集中在哪几个文件（列出绝对路径）
- **公共设计模式**：把多场景共用的套路抽出来编号（如"模式① 规范化 schema""模式② 标志列"），并解释每个取舍的**根因**
- **方案演进史表**：A→B→C 各方案做法与结局，防止接手人走回头路
- **术语表**：编号体系（如 `C0~C9`/`D2~D9`）要注明"编号只在各自文档内有效，跨文档不通用"

### `02-<多场景>对比.md` — 横向对照
- **总览大表**：把 15~20 个维度横向铺开（接口、分支、数据源、字段、关联键、是否修复、状态、文档路径…）
- **逐场景详解**：每个场景一节，含①对比链路图 ②环节与字段表 ③该场景的特殊点
- **差异溯源表**：最后用一节回答"为什么它们设计不一样"，逐条给根因

> 链路图用纯文本箭头画（``` 代码块），比图更易维护、可 diff。

### `03-资料索引.md` — 出处与用途
- 按类别分节：方案文档 / 脚本 / 需求来源 / 配置实况 / 操作指引 / 外部规范 / 测试材料 / 项目台账 / 关键源码
- 每张表列：**文件 / 用途 / 可信度 / 最后更新**
- **可信度分级**：★★★ 源码或数据库实测 ｜ ★★ 方案文档（已评审） ｜ ★ 原始需求或外部规范
- **配置 dump 要给时间线表**（按时间戳排序），能据此推断真实进度
- 结尾加「**我要做 X，该看哪个**」速查表

### `04-进度与待办.md` — 状态与优先级
- **完成状态矩阵**：工作项 × 场景，状态用固定口径：
  `✅ 已完成`（源码/DB 可验证）｜`📄 已备未用`（写好了没落地）｜`❌ 未做`｜`❓ 待核实`（导出范围外，无法判定）
- **待办清单**：编号 `HO-<场景>-<序号>`，括号内标注原方案编号便于回查；列 事项/类型/依赖/完成判据
- 按 **P0（阻塞）/ P1（核心推进）/ P2（收尾）** 分组
- **优先级总表**：含"卡在哪"列
- **阻塞项汇总**：含"需向谁确认"列
- **建议接手节奏**：分步骤，标明哪些可立即做、哪些要等外部答复
- 结尾附项目 `AGENTS.md` 的交付门禁要求

### `05-风险与缺口.md` — 动手前必过
1. **代码与文档不一致项**：每条含「文档怎么说 / 实测结果 / 后果 / 修复方式 / 对应待办编号」
2. **未验证项表**：明确标注"待实机回归"，并说明受阻原因
3. **环境限制与硬约束**：无构建工具、禁止访问的地址、禁忌命令
4. **易踩坑提示**：设计层面的坑，每条给"❌ 错误做法 / ✅ 正确做法"
5. **技术风险清单**：编号 + 场景 + 说明与缓解
6. **交接自检清单**：可勾选的 checkbox

## 写作纪律

- **状态必须有证据**：写"已落地"就要能指出源码位置；写"未做"就要能说明搜索方式。无法判定的写 `❓ 待核实`，**不要猜**。
- **不要照抄方案文档的自我评价**。方案文档常有"已落地""已补"的乐观表述，交接文档的职责是核对。
- **给根因，不只给结论**。接手人需要的是"为什么这么设计"，才能在未来改动时不破坏设计。
- **缺口要给修复方式**，不只是指出问题。
- **跨文档引用用相对链接**（`[`04-进度与待办.md`](04-进度与待办.md)`），交接包内部可跳转。
- 中文撰写；表格优先于长段落；单文档控制在 8~14 KB。

## 完成后

1. 用 `present_files` 展示交接包（README 放第一位）
2. 向项目 `agent_memory/` 追加一条日志
3. 若发现台账口径过期，在交接文档中明确指出（**不要**擅自改台账，除非用户要求）

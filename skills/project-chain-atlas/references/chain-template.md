# 每条链路的固定骨架

统一骨架的价值：读者读到第二页时不用重新适应结构，注意力全放在内容上。
**不要为了「显得丰富」而增删小节**——增减会让读者失去预期。

## 四要素的写法要求

### 起点

写清**三件事**：谁触发（用户 / 定时器 / 消息 / 另一条链路）、以什么形式（HTTP 方法 + 路径 /
函数调用 / 事件名）、前置条件（必须先有什么）。

反例：「用户点击按钮」——太粗，读者不知道是哪个接口。
正例：「用户点『发起研究』→ `POST /api/v1/research/run`，body 含 question / thread_id? / hitl_enabled?」。

### 关键节点

**用编号写顺序**，并把「顺序为什么是这个顺序」在需要时点出来。
顺序往往是正确性关键——例如「先落检查点与请求事件，再切状态」是为了避免查询方看到中间态。

每个节点写「做什么 + 在哪（file:line）」的浓缩形式，不要把代码抄进来。

### 分支

这是最容易被写漏、也最有价值的部分。至少覆盖：

- **正常岔路**：条件 A → 走 X；条件 B → 走 Y
- **失败岔路**：校验失败 / 权限不足 / 并发冲突 / 依赖不可用 → 各是什么结局
- **降级岔路**：外部依赖挂了 → 退化到什么行为、留什么痕

### 终点

写清**状态**（终态枚举值）与**持久化痕迹**（落了哪些表 / 哪些缓存键）。
读者据此判断「我怎么知道它跑完了 / 跑成了没有」。

## 图解的要求

- **用成熟 DSL 写、构建期预渲染成静态 SVG 内联**（Mermaid / D2 / Graphviz / PlantUML）。
  不在页面里引图表运行时——单文件必须离线可开。渲染与回填命令见 `html-atlas-spec.md`。
- 一张图**只表达一条链路**；节点控制在 6~12 个，超了就拆页。
- 用**颜色编码层次**（前端 / API / 编排 / 智能体 / 事件 / 存储），全篇保持一致
  （在 DSL 里用 `classDef`，或在 CSS 里覆盖）。
- 分支要能区分（正常分支实线、失败 / 降级分支虚线 + 红色）。
- 图里的节点做成**可点击**（DSL 链接指向 `#p-xxx`），读者才有「顺着走」的体验。

---

## 代码实例的要求

**摘最能说明问题的那几行**，并标 `file:line`。

- 优先摘：顺序关键处、并发裁决处、降级收口处、幂等保证处。
- 不要整段贴：既会立刻过时，也把读者淹了。
- 保留原注释里解释「为什么」的那几句——它们往往比代码本身更有信息量。
- 如果代码里有反直觉的写法（例如「两条失败路径都要跑一次等价计算」），
  一定要摘出来并解释原因。

---

## 关联与触发条件

在页面末尾（或四要素里的「关联」行）标注：

- **上游**：谁触发我
- **下游**：我触发谁
- **前置**：我必须先满足什么

有了这三项，读者才能把单页放回整体图景。

---

## 篇幅控制

| 链路复杂度 | 建议篇幅 |
|---|---|
| 简单（3~5 个节点） | 半屏：四要素 + 1 张图 + 1 段代码 |
| 中等（6~10 个节点） | 1~2 屏：四要素 + 1~2 张图 + 2~3 段代码 |
| 复杂（含多分支/多轮循环） | 拆成主链页 + 各分支页 |

**判据**：如果一页需要读者滚动超过 3 屏才能看完，说明该拆了。

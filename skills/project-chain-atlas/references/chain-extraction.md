# 如何从源码切出链路

链路不是「读一遍代码就自然浮现」的东西，它有明确的切法。这份文档给的是可复用的读法。

---

## 一、先建立三类坐标

### 1. 入口坐标（链路天然的起点）

| 类型 | 找法 | 为什么是起点 |
|---|---|---|
| HTTP 端点 | 路由注册处（`include_router` / `app.get` / `@Controller`） | 用户动作的入口 |
| 定时 / 后台任务 | 进程启动钩子（`lifespan` / `onModuleInit` / `main`）里的 `create_task` / `setInterval` | 系统自发行为的起点 |
| 消息消费者 | 队列消费循环（`xreadgroup` / `consume` / `@KafkaListener`） | 异步链路的接续点 |
| 启动钩子本身 | `lifespan` / `bootstrap` / `ApplicationRunner` | 自检、恢复、资源装配 |

把入口全部列出来，标上「谁调用它」——这一步做完，链路清单已经完成一半。

### 2. 状态坐标（链路的实质是状态迁移）

找出所有**持久化载体**并记下它们的键 / 表名：

- 关系库表（尤其带唯一索引和状态列的——状态机通常就藏在这里）
- 缓存键（含 TTL 与失效策略）
- 队列 / 流（含消费组、重试、死信）
- 对象存储的键规则
- 检查点 / 快照（框架自管的也要算）

**为什么必须单独做这一步**：链路图里「箭头」的实质是「状态从 A 载体搬到 B 载体」。
不做这一步，画出来的图会变成「函数调用图」，读者仍然不知道数据在哪。

### 3. 横切坐标（每条链路都会穿过的）

认证、限流、事件发射、日志与 trace、错误映射、动态配置。

它们不专属于任何一条链路，但要**单独成链路**，并在每条业务链路里标注「在此处穿过 X」。
漏掉它们的后果：读者按图去查问题时，会发现线上行为与图对不上（因为限流/鉴权被省略了）。

## 二、沿数据流走，而不是沿目录走

**错误做法**：打开 `src/`，对每个子目录写一节「这个模块干什么」。
结果是一份模块清单，读者读完不知道「我点一下按钮之后发生了什么」。

**正确做法**：从入口出发，跟着数据走完一趟，把路径上碰到的每个环节记下来：

```
用户动作 → 参数校验 → 权限判定 → 落库(表A) → 起异步任务 → 出队 → 调外部服务
        → 落库(表B) → 发事件 → 推送 → 前端渲染
```

走完一趟，你会自然得到：起点、关键节点、分支、终点。

### 必须停下来问的四个问题

每到一个节点都问：

1. **顺序有约束吗？** 「先落库再发通知」还是反过来？为什么？（这类顺序往往是正确性关键，
   例如先写检查点再切状态，否则查询方会看到中间态）
2. **失败了怎么办？** 抛错终止？降级继续？重试？进死信？——**降级也是链路**。
3. **并发下谁说了算？** 应用层预检只是快速失败，最终裁决往往是数据库唯一索引 / 乐观锁 / 分布式锁。
   把「谁说了算」标出来，读者才敢改。
4. **幂等吗？** 重复执行会怎样？（事件重放、消息重投、请求重试都会触发这个问题）

## 三、穷举检查（三问法）

写完第一版清单后，用这三问逼出遗漏：

**问一：用户能做的每个动作，走完了吗？**
把前端界面上所有可点元素列出来（按钮、菜单项、开关、上传区、下拉框），逐个问「点了之后呢」。
这一步最容易发现「有界面但没写进文档」的链路。

**问二：系统被动响应的每条路，走完了吗？**
断线重连、刷新页面恢复、进程重启、组件故障、任务超时、缓存失效、配额耗尽。
这些没有用户动作触发，但它们是真实链路，且往往是事故现场。

**问三：每条链路的失败分支，走完了吗？**
校验失败、并发冲突、权限不足、依赖不可用、超时、数据缺失。
判据：**如果一条链路只画了 happy path，它就不完整。**

---

## 四、链路粒度

| 信号 | 处理 |
|---|---|
| 单条链路写下来超过 2~3 屏 | 拆成「主链」+「子分支」多页 |
| 两条链路共享 80% 的节点 | 合并为一条，用分支区分 |
| 一条链路只跨 1 个文件、无状态迁移 | 不单独成链路，并入调用它的那条 |
| 同一条逻辑有「同步版」和「异步版」 | 各成一条（如上传后「即时投递」vs「轮询补偿」） |

---

## 五、标注链路之间的关系

这一步决定读者能否建立**整体图景**，而不是记住一堆独立流程。

对每条链路标注：

- **上游**：谁触发我（用户动作 / 定时器 / 队列消息 / 另一条链路）
- **下游**：我触发谁
- **共享资源**：我和哪条链路争同一个锁 / 表 / 队列
- **前置条件**：我必须先满足什么（例如「必须先有检查点」）

最后画一张**总关系图**：以「主动脉」（最核心的那条链路）为中心，
其它链路要么给它送输入，要么消费它的输出。这张图放在手册最前面，读者先看它再逐条深入。

---

## 六、常见遗漏（自查表）

- [ ] 鉴权 / 限流（横切，易被当成「框架自动做的」而漏掉）
- [ ] 事件 / 日志 / trace 的发射链路
- [ ] 异步任务的**投递**与**消费**（两段，常只写一段）
- [ ] 补偿 / 对账 / 重试 / 死信
- [ ] 删除链路（往往比创建链路更复杂，涉及多处存储的一致清理）
- [ ] 启动恢复（进程重启后怎么收尾上次的残留）
- [ ] 配置热更新对运行中任务的影响（快照 vs 实时读取）
- [ ] 导出 / 下载（常带额外的门禁或限流）

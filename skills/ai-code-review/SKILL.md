# AI生成代码专项审查技能

## 1. 技能定位

本技能用于审查AI（LLM/大模型）生成的代码，聚焦AI代码特有的风险模式。
与项目规范审查互补，不重复检查代码风格、命名规范等已有规则覆盖的内容。

---

## 2. 审查维度与检查清单

### 2.1 幻觉与虚构问题（Hallucination）
AI代码最典型的失败模式——"看起来对，实际上不存在"。

| 检查项 | 具体做法 | 风险等级 |
|--------|---------|---------|
| **虚构API/方法** | 对不熟悉的库函数，强制要求提供官方文档链接；检查import是否真实存在 | 🔴 高 |
| **虚构依赖包** | 验证`package.json`/`requirements.txt`/`pom.xml`中新增依赖是否真实存在、是否被官方维护 | 🔴 高 |
| **虚构配置项** | 检查配置文件中的参数名是否在官方文档中有定义 | 🟡 中 |
| **过时的API** | 确认使用的API版本是否为当前稳定版本，非已废弃接口 | 🟡 中 |

**审查话术**："这个方法/包我在官方文档中没找到，请提供引用链接。"

---

### 2.2 安全漏洞（Security）
研究显示47%的AI生成代码存在安全漏洞，审查时必须优先检查。

#### A. 输入验证缺失（最常见）
- [ ] 所有用户输入是否经过校验（类型、长度、范围、格式）
- [ ] 是否存在直接拼接SQL/命令/OS调用的字符串
- [ ] 文件路径是否做了限制（防止目录遍历）
- [ ] 反序列化操作是否对数据来源做了验证

**典型模式**：AI生成的代码常假设输入合法，除非明确要求否则不加校验。

#### B. 认证与授权
- [ ] 新生成的接口是否默认暴露为公开端点
- [ ] 是否缺少身份认证中间件
- [ ] 权限校验是否完整（特别是管理员/敏感操作）
- [ ] 密码是否使用现代哈希算法（Argon2/bcrypt），非明文或MD5

#### C. 密钥与凭证
- [ ] 是否存在硬编码的API Key/密码/Token
- [ ] 配置文件中的敏感信息是否使用环境变量/密钥管理服务
- [ ] 日志中是否可能打印敏感信息

#### D. 不安全默认值
- [ ] CORS策略是否过于宽松（`*`）
- [ ] 文件上传是否限制类型和大小
- [ ] 错误信息是否向客户端暴露内部细节（堆栈跟踪、SQL语句等）

---

### 2.3 逻辑正确性（Logic Correctness）
AI代码能运行但结果可能错误——"非语法错误，但行为错误"。

| 检查项 | 说明 | 审查方法 |
|--------|------|---------|
| **边界条件** | 数组越界、空指针、除以零、整数溢出 | 检查循环边界、空值处理 |
| **并发安全** | 竞态条件、死锁、非线程安全操作 | 检查共享资源访问、锁粒度 |
| **事务完整性** | 多表操作是否加事务、异常时是否回滚 | 检查`@Transactional`或等价机制 |
| **业务语义** | 代码是否真正实现了需求意图，而非"看起来相关" | 对照需求文档逐行验证 |
| **精度问题** | 金额计算是否使用Decimal/BigDecimal，非float/double | 检查金融/数值计算 |
| **状态流转** | 状态机转换是否完整、是否有非法跳转 | 检查状态变更逻辑 |

---

### 2.4 依赖与供应链风险
- [ ] 新增依赖是否经过团队审批
- [ ] 依赖版本是否有已知CVE漏洞（使用`npm audit`/`safety`/`Dependabot`扫描）
- [ ] 是否引入了不必要的重量级依赖（AI倾向于"多装一个包解决问题"）
- [ ] 许可证是否合规（GPL等传染性协议）

---

### 2.5 可维护性与架构
- [ ] 是否生成"孤岛代码"——与现有架构风格不一致、难以维护
- [ ] 是否过度复杂化（AI倾向于生成比人类更复杂的代码）
- [ ] 是否有死代码/未使用的变量和导入
- [ ] 错误处理是否完整（AI常忽略错误分支或简单`catch`后静默吞掉）
- [ ] 是否缺少必要的日志、监控、链路追踪埋点

---

### 2.6 性能隐患
- [ ] 循环中是否有数据库查询/N+1问题
- [ ] 是否加载全表数据到内存（无分页）
- [ ] 是否有重复的外部API调用
- [ ] 大数据量操作是否考虑批量处理

## 3. 审查流程（推荐）

```
Stage 1: 自动化扫描（前置）
├─ 静态安全扫描（Semgrep/SonarQube/Bandit）
├─ 依赖漏洞扫描（Snyk/Dependabot）
├─ 单元测试（覆盖happy path + edge cases）
└─ 幻觉检测：编译/运行验证所有新引入的API

Stage 2: 人工审查（本技能）
├─ 安全优先：按2.2清单逐项检查
├─ 逻辑验证：按2.3清单验证业务正确性
├─ 依赖确认：按2.4清单验证所有新增依赖
└─ 架构适配：按2.5检查与现有系统的兼容性

Stage 3: 集成验证
├─ CI/CD流水线是否通过
├─ 与现有监控/日志系统是否集成
└─ 回滚策略是否就绪
```

## 4. 审查标记规范

在PR/MR评论中使用统一标记：

| 标记 | 含义 | 处理方式 |
|------|------|---------|
| `[AI-SECURITY]` | AI代码安全风险 | 必须修复，阻塞合并 |
| `[AI-HALLUCINATION]` | 疑似虚构API/依赖 | 必须提供官方文档证明 |
| `[AI-LOGIC]` | 逻辑正确性疑问 | 需补充测试用例或说明 |
| `[AI-DEPS]` | 依赖/供应链问题 | 需安全团队审批 |
| `[AI-MAINTAIN]` | 可维护性问题 | 建议修复，非阻塞 |

## 5. 特殊场景加强审查

### 5.1 认证/支付/敏感数据处理
- 必须双人审查
- 安全团队必须参与
- 禁止直接采用AI生成的加密/哈希/认证逻辑，必须使用团队已审批的库

### 5.2 全栈/脚手架代码
AI生成完整服务时，特别容易：
- 默认开放所有端点
- 跳过认证中间件
- 使用开发环境配置（DEBUG=True, 宽松CORS）

**审查重点**：检查所有路由/端点的访问控制；检查所有配置文件的环境区分。

### 5.3 规则文件（.cursorrules/.github/copilot-instructions.md）
- 警惕隐藏的提示注入（不可见Unicode字符、异常格式）
- 审查标准应与可执行代码同等严格
- 规则文件可能被用于在生成代码中植入后门或泄露敏感信息

## 6. 度量与持续改进

建议跟踪以下指标：
- **AI代码缺陷率**：AI生成代码 vs 人工代码的bug密度对比
- **安全漏洞检出数**：按2.2分类统计
- **幻觉事件数**：虚构API/依赖的发生频率
- **审查耗时**：AI代码审查是否比人工代码耗时更长（通常初期会更长）

定期回顾这些数据，更新本技能的检查清单。

## 8. 整合能力：结构化代码审查 / 安全审查 / 简化（并入自 code-review · security-review · simplify）

> 原独立的 `code-review`、`security-review`、`simplify` 三个技能已**并入本技能**，统一通过 `ai-code-review` 触发，避免多技能分散引用与缺失。以下为其能力清单与执行要点。

### 8.1 结构化代码审查流程（code-review）
提供可调节力度的标准代码审查工作流，适用于所有（含非 AI 生成）代码。

- **审查力度（intensity）**
  - `quick`：仅检查 P0 正确性 + 明显安全/幻觉问题，适合小型改动、Hotfix。
  - `normal`：覆盖 P0–P2（正确性/安全性/可维护性），适合常规 PR。
  - `deep`：覆盖 P0–P3 + 架构适配 + 性能 + 依赖供应链，适合核心模块/重构/对外接口。
- **结构化审查阶段**
  1. 范围界定：确定审查对象（PR/文件/模块）与变更类型（功能/重构/修复/配置）。
  2. 逐维度扫描：按 P0→P3 优先级依次检查（见 §2 与下方维度）。
  3. 发现验证：每个问题必须可复现，标注置信度 CONFIRMED / PLAUSIBLE / UNCERTAIN。
  4. 输出报告：按「输出规范」给出文件:行号、根因、可操作修复建议，并汇总必须修复/建议优化/需讨论数量。
- 触发：任何标准代码审查任务，无论是否 AI 生成。

### 8.2 安全审查专项（security-review）
全面安全审查，覆盖认证、授权、注入、数据泄露等，作为第一级安全能力（与 §2.2 互补）：

- 认证与授权：接口是否默认公开、是否缺身份认证中间件、权限校验完整性（管理员/敏感操作）、密码是否现代哈希（Argon2/bcrypt）。
- 注入类：SQL/NoSQL 注入、命令注入、XSS、LDAP/XXE 注入；输入是否经过类型/长度/范围/格式校验。
- 敏感数据：硬编码密钥/Token、日志中 PII 泄露、配置文件是否使用密钥管理、错误信息是否暴露内部细节。
- 不安全默认值：CORS 过宽（`*`）、文件上传未限类型大小、DEBUG/宽松配置残留。
- 不安全的反序列化与路径遍历。
- 触发：涉及认证、支付、敏感数据、对外接口时**必须**启用（部分场景要求双人 + 安全团队参与，见 §5.1）。

### 8.3 简化检查（simplify）
聚焦代码简洁性与抽象质量，识别可简化、可复用之处：

- 代码复用：重复逻辑是否可抽取为公共函数/工具；是否重复实现已有能力。
- 简化：过长函数、过深嵌套、复杂条件是否可拆解；是否可用标准库/语言特性替代手写。
- 效率：是否存在冗余计算、可合并的循环/查询、不必要的内存分配。
- 抽象层级：抽象是否恰当（不过度抽象也不过度具体）；是否违反 KISS/YAGNI。
- 触发：审查可维护性（P2）时自动应用，或显式要求「简化这段代码」。

## 9. 使用方式

1. 将此技能作为项目规范审查的**补充流程**
2. 仅当PR包含AI生成代码时触发（可要求提交者标注`[AI-GENERATED]`）
3. 审查者按本清单逐项检查，使用统一标记评论
4. 阻塞项（SECURITY/HALLUCINATION）必须修复后方可合并

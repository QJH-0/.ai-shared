# 按最新代码重写项目文档与简历面试文档

## 适用场景

- 「根据最新代码重写 README 和 D:\01resume\简历\面试准备\08-xxx」
- 项目经历一轮重构/迭代后，文档里的架构描述、数字、代码引用已过时
- 需要把仓库里的专题文档同步到简历目录

## 铁律（先记这三条）

1. **数字必须实测**：测试通过数、耗时这类能跑的，先跑出来再写。跑不到的（需真实 LLM/中间件）标为「未实测」，**不要编造也不要用推断值冒充实测值**。
2. **改文档前先找过时点**：用 `git log --since` 看文档日期之后有哪些改动，再用 grep 在旧文档里搜旧术语（`grep -n "旧节点名\|旧数字\|旧配置项" *.md`）。这一步能定位到所有要改的地方，比通读快得多。
3. **选材铁律（简历类文档）**：难点必须来自**客观约束**（协议/标准限制、语言机制、算法固有矛盾、平台差异、分布式一致性），**不能来自自身疏忽**。缺陷类素材只能转化为「我建立了什么机制」。

## 工作流

### 1. 取实测基线（并行跑，别等）

```bash
# 后端（示例为 deepresearch 项目，按项目实际命令替换）
python -m pytest app/test --ignore=app/test/test_fix_regressions.py -q
# 前端
cd <front_dir> && npx vitest run
```

拿到 `N passed, M skipped` 与耗时。旧文档里的数字一律以本次为准。

### 2. 列出文档日期之后的改动

```bash
git log --since="<文档日期>" --date=short --pretty="%h %ad %s" | head -60
git status --porcelain -uall    # 顺带确认工作区干净
```

### 3. 读关键源码（不要通读，挑锚点文件）

挑能决定文档骨架的文件：图拓扑 / State / 模型工厂 / 主服务 / 事件协议 / 配置文件。读完从源码里摘出「事实锚点」清单（节点名、判定条件、阈值、字段名），后面所有文档都以这份清单为准。

### 4. 扫旧文档的过时表述

```bash
grep -n "旧节点名\|旧配置项\|旧数字\|旧函数名" *.md | head -50
```

产出一份过时清单，重写时逐条对照。

### 5. 确认范围（文档量大时必问）

超过 3 个文件或 20 万字符时，先用 AskUserQuestion 问三件事：
- 重写范围（全量 / 核心几篇 / 先出差异清单）
- 仓库已有专题文档是否同步进简历目录
- 数字口径（实测为准 / 沿用旧数字 / 改为定性描述）

### 6. 重写

- 先写 README（事实密度最高、篇幅最小，能锁定口径）
- 再写简历/面试文档，每个文件顶部用一段「与上一版的差异」开头，让读者（三天后的自己）立刻知道变了什么
- 文档里统一标注证据等级：A 实测 / B 代码事实 / C 未实测

### 7. 同步仓库专题文档

```bash
cp -f docs/interview/*.md "D:/01resume/简历/面试准备/<项目目录>/"
```

### 8. 顺手修项目约定文件

`AGENTS.md` / `CLAUDE.md` 这类文件常和代码一起过时（架构描述、测试基线、踩坑记录）。改完主文档后扫一遍并修正——它们会误导后续所有会话。

## 常见坑

- **Write 覆盖已存在文件前必须先 Read**（工具硬约束）。长文件用 `Read` + `limit` 读前几行即可满足。
- **文档日期 vs git 提交日期不一致**：简历目录的文件可能是仓库文档的旧副本，用 `md5sum` 对比确认哪些需要先同步。
- **评测类数字最容易失真**：注意区分「指标算出来了」和「指标有效」。检查题集判别力、是否有标注缺失导致指标不产数。
- **别忘了嵌套仓库**：项目根下若有 `参考项目/` 之类含独立 git 仓库的目录，勿在根执行影响全树的 git 操作。

## ⭐ 交付后复查（最关键的一步，别跳过）

写完先跑这两步，实测每次都能抓出问题：

```bash
# 1. 回扫：对重写后的文档 grep 旧术语
grep -n "旧节点名\|旧数字\|旧配置项\|旧函数名" *.md

# 2. 回核：挑几个从代码推出的事实回核（节点数、常量表、字段数）
grep -c "add_node" <graph文件>        # 节点数
sed -n '/^NODE_LABELS/,/^}/p' <服务文件> | grep -c '":'   # 常量表项数
```

**为什么第 2 步不可省**：文档里写的「N 个 X」经常是我从代码**推断**的，回核能抓出「我以为是、其实不是」。
一次实战里，回核 `NODE_LABELS` 发现只有 9 项而节点有 10 个——**漏了一个新节点的中文标签**，这是代码缺陷不是文档问题。

改了代码就要跑测试；改了常量先 grep 确认没有测试锁它。

## 交付前自检

- [ ] 所有数字都能追溯到本次实测或明确标为未实测
- [ ] 旧文档里的过时术语已全部替换（用第 4 步的 grep 复验）
- [ ] 从代码推断的「N 个 X」已逐条回核
- [ ] 每篇文档顶部写明与上一版的差异
- [ ] 仓库专题文档已同步（用 `md5sum` 确认两边一致）
- [ ] 项目约定文件与仓库内其他简历向文档的过时表述已修正
- [ ] 历史阶段文档（`docs/dev/Phase*` / `archive/`）**不动**——改了就丢了开发脉络
- [ ] 已追加工作区记忆日志

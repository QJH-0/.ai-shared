# 断链审计法（Broken Chain Audit）

## 适用场景

- 接手他人项目做代码审查，需要在有限时间内定位真问题
- 用户反馈「某功能好像没生效」，但代码看起来是对的
- 测试全绿、门禁 PASSED，但功能表现不符合预期
- 修完一批 bug 后，要确认没有同类漏网

## 核心判断：这类代码的典型特征

**失败路径都有 `except` 兜底** → 测试全绿、日志只有 warning、功能静默降级。
所以「测试通过」和「门禁通过」不能证明行为正确，只能证明「接口存在、契约不抛异常」。

## 五个高命中率的 grep（按优先级）

### 1. grep 私有 helper 的调用点 → 找死代码

对每个 `_` 开头的函数/模块级常量，数它在**全仓**的出现次数（排除自身定义行）：

```bash
grep -rn "\b_func_name\b" --include=*.py . | grep -v __pycache__
```

只出现 1 次（就是定义处）= 死代码。
**关键**：死代码往往还带着「🔧 修复 #xxx」的注释 —— 说明有人修过但没接线，
于是「修好了」的注释和「没生效」的代码同时存在，最容易误导后续维护。

### 2. grep 关键字段的写入点 → 找 read-without-write 断链

挑出被读取的字段名（如 `relevance_score`、`doc_id`、`parent_id`），
分别 grep 写入点和读取点：

```bash
grep -rn "relevance_score" --include=*.py app/
```

若写入点全在死函数里，或写入点数为 0 → 读取方拿到的永远是默认值。
**级联效应要跟到底**：某字段恒为默认值 → 依赖它的判断分支恒走同一支 →
产生稳定且误导的错误行为（例如永远报「证据不足，最高仅 0.00」）。

### 3. grep 同名函数 → 找重复实现（最危险的一类）

```bash
grep -rn "def build_agents\|def _semantic_split" --include=*.py app/
```

同名实现出现在两个模块时，**必须先确认哪个是活的**，再决定改哪个：

```bash
grep -rn "import build_agents\|from .* import build_agents" --include=*.py app/
```

血的教训：把配置修复打进了一个「只有测试在用」的副本，
生产路径仍带着原缺陷，而测试全绿掩盖了这一点。

### 4. 检查测试是否固化了错误行为

三个高危信号：

- **fixture 里有真实数据不存在的字段**：`test_evidence_scorer.py` 的记录构造带
  `"query"` 字段，而生产数据从无该字段 —— 正是它让「评分 prompt 问题恒为空」长期未被发现
- **断言写死了实现细节**：`assert kwargs.get("namespace") == ("memories", "{user_id}")`
  固化了错误的命名空间顺序
- **按源码文本断言**：`assert 'raise_interrupt("clarification"' in src` ——
  这类审计测试最容易把 bug 锁死

修复时**必须同步纠正这些断言**，否则改动会被测试挡住，或缺陷再次静默回归。

### 5. 检查跨模块契约的两端是否真的一致

- 后端发的事件 payload 键 vs 前端读的键（`payload.draft` vs 后端发 `full_report`）
- 写入侧的命名空间/键 vs 读取侧（`("memories", uid)` vs `(uid, "memories")`）
- `kind`/`type` 这类「类型标识」是否被两个语义不同的点共用（会导致载荷结构冲突）

## 非破坏性实机验证手法

不要用「读代码推断」下结论，也不要污染生产数据：

- **临时集合/临时目录**：在真实中间件上建 `__probe_xxx__` 集合，验证完立即 drop
- **探针脚本**：用最小 StateGraph / 最小对象验证框架行为
  （例：实测 langgraph 对未知 state key 是**静默丢弃**而非抛错，避免了一次错误定级）
- **必然无匹配的表达式**：验证删除接口可用性时用 `expr='doc_id == "__probe_none__"'`
- **对比实验**：怀疑某个开关导致差异时，同时跑「默认值」与「显式值」两组，打印实际 schema/字段

## 报告分级建议

| 级别 | 判定标准 |
| --- | --- |
| P0 | 凭据入库、无鉴权/越权、数据不可恢复 |
| P1 | **「宣称可用但实际断链」的链路**（功能是坏的，但没人知道） |
| P2 | 逻辑错误、级联误判、设计缺陷（有 workaround） |
| P3 | 死代码、命名、重复实现、文档过期 |

P1 的判定关键是：**它是否让产品的宣称能力失效**。这类问题优先级高于多数「代码风格」类问题。

## 修复阶段的三条纪律

1. **先确认改的是活代码**（见手法 3）
2. **每项修复配一条「失败即代表缺陷复现」的回归断言**，写清注释说明原缺陷
3. **修完跑全量测试**；若某个测试失败，先判断它是「固化旧行为」还是「真的回归」——
   前者应连同断言一起纠正，并在报告中列明

## 常见陷阱

- 把「测试通过」当作「功能正确」
- 只看单个文件就下结论（断链必然跨模块）
- 用 `except` 兜底的失败路径当正常路径读（会漏掉静默降级）
- 改动只落到副本实现上
- 删除文件前不核对内容归属（「同名」不等于「同内容」）

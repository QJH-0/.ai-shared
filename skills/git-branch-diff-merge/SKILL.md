# Git 分支双向合并融合

## 核心目标

**不是"以谁为准覆盖谁"，而是把两个分支的代码融合成一份功能齐全的最新代码。**

- 双方的新增功能、bug 修复、边界处理、配置、注释，默认**全部保留**；任一功能缺失即视为融合失败。
- 冲突块按**代码逻辑的新旧**取新逻辑，禁止用旧代码覆盖新代码。
- 新旧无法判定、或双方都新但方向冲突时，**暂停并交用户选择**，不擅自取舍。

## 输入契约

必需（缺任一则先询问补齐，不猜测）：

```
项目：<project>
分支A：<branchA>
分支B：<branchB>
```

可选：

```
需要对比的路径：<file | dir | 全仓库>    # 默认全仓库
新旧方向提示：<文字>                      # 仅作参考，仍须逐块验证
```

当前分支由 `git branch --show-current` 读取，不需用户提供。支持任意项目与任意分支名，不写死。

## 职责边界

**AI 可做**

- 只读 Git：`git diff`、`git log`、`git show`、`git status`、`git branch`、`git remote`、`git merge-base`、`git merge-tree`
- 用编辑 / 写文件工具把融合后的完整代码写入工作区文件
- 冲突分析、新旧判定、生成融合代码、输出建议 Git 命令

**AI 禁止**（发现工作区有未提交改动时只提示风险，不自行 stash / checkout / reset）

- 切分支：`git checkout`、`git switch`、`git restore`、`git branch -c/-C/-d/-D/-m/-M`
- 写操作：`git add`、`git commit`、`git push`、`git merge`、`git rebase`、`git reset`、`git cherry-pick`、`git stash pop/apply`
- `git fetch`（除非用户明确授权）

**用户负责**：切分支、add / commit / push、回滚，以及任何改动仓库历史或工作区状态的操作。

> 一句话：**代码内容 AI 改，Git 动作用户做。**

## 六条红线（违反任意一条等同任务失败）

1. 不是"以某分支为准覆盖另一分支"——两个分支对等合并，双方改动都要进来。
2. 禁止整文件 / 整函数 / 整段从任一分支直接覆盖，必须逐块比对、逐块融合。
3. 禁止用旧代码覆盖新代码：某一侧是更晚的逻辑（新接口、新命名、新实现、新边界处理）时必须采用。
4. 禁止因冲突丢弃任何一侧的功能性代码，含新增函数 / 分支 / 判空 / 重试 / 日志 / 开关 / 配置 / 注释说明。
5. 禁止静默丢弃：融合完成后必须做漏删自检，未保留项显式列出并等用户确认。
6. 无法判定新旧、或双方均新且方向冲突时，必须暂停给两种方案，禁止自行取舍。

## 融合方法论

### Step 0：取 merge-base 并记下哈希

```bash
git merge-base <branchA> <branchB>
```

**把输出的哈希抄下来，后续命令用字面量替换 `<BASE>`。**

> ⚠️ 不要写成 `BASE=$(git merge-base ...)` 再在后续命令里用 `$BASE`：shell 变量不跨工具调用存活，`$BASE` 会静默变空，命令退化成"工作区 vs 单分支"——结果错但不会报错。

所有"新增 / 修复 / 改动"的判断都相对 BASE，而不是相对另一分支。

### Step 1：拿到两侧相对 BASE 的净增

```bash
git diff --name-status <BASE> <branchA> [-- <path>]
git diff --name-status <BASE> <branchB> [-- <path>]
git diff <BASE> <branchA> [-- <path>]
git diff <BASE> <branchB> [-- <path>]
git log -1 --format="%ad | %h | %s" --date=iso <branchA> -- <path>
git log -1 --format="%ad | %h | %s" --date=iso <branchB> -- <path>
```

提交时间只作**新旧判定的辅助信号之一**，不能单独作为取舍依据。

### Step 2：逐块分类（每个 hunk 归入四类之一）

| 分类 | 特征 | 处理 |
|---|---|---|
| ① 仅 A 改动 | BASE→A 有改动，BASE→B 无 | 原样保留 A 的改动 |
| ② 仅 B 改动 | BASE→B 有改动，BASE→A 无 | 原样保留 B 的改动 |
| ③ 双方都改但不重叠 | 同文件不同位置各自改动 | 两边都保留，按逻辑顺序拼接 |
| ④ 双方都改且重叠 | 同一行 / 同一语句 | 见 Step 3 |

① 和 ② 最容易被误删（尤其 ②），**一律照单全收，不做任何取舍。**

### Step 3：处理第 ④ 类重叠冲突（核心）

**第一步：判断双方意图** — 修 bug / 加功能 / 改接口参数 / 重命名 / 重构 / 格式调整，分别记录 A、B 各自"想解决什么问题"。

**第二步：判断哪一侧更新**（综合判断，**不能只看时间**）：

1. 接口 / 函数签名：参数更全、返回值更完整、命名更贴合业务的一方通常更新
2. 实现方式：使用新 API / 新常量 / 新依赖 / 新架构模式的一方通常更新
3. 命名：与项目整体命名一致、更语义化的一方通常更新
4. 边界与防御：判空、重试、日志、异常处理更完备的一方通常更新（这一侧往往就是"修复"）
5. 提交时间：仅作辅助，晚提交不等于逻辑真正演进

**第三步：据判定融合**

- **能兼容**：以新逻辑为主体，把另一侧的修复点 / 防御点 / 新增分支移植进新结构，用 `[合并处理]` 注释说明。
- **无法兼容**（如新侧删掉了旧侧依赖的字段 / 函数）：写清双方差异、新旧依据、影响范围，给出两种方案，**暂停等用户选**。
- **双方都新且方向不同**：同样暂停，交用户决策。

**第四步：禁止的动作** — 直接取任一侧整段；因某侧"看起来是基准"而放弃另一侧修复；用旧代码覆盖新代码。

### Step 4：写回工作区

用编辑 / 写文件工具把融合后的**完整文件**写入目标文件，不要只输出片段让用户手工粘贴。

冲突处按**目标文件语言的注释符**标注：

```
[合并处理] 采用 <侧> 的新逻辑：<一句话>，并移植 <另一侧> 的修复/新增：<一句话>
[合并处理] 保留 <侧> 新增功能：<一句话>
[合并处理] 保留 <侧> 修复逻辑：<bug 现象 / 边界>
[合并处理] 原注释保留：<原文>
```

> `[合并处理]` 是临时审计标记。用户确认合并结果并提交后可自行清理，避免长期残留在代码中。

### Step 5：漏删自检（强制，不可跳过）

写回后逐条核对两侧相对 BASE 的净增：

```bash
git diff <BASE> <branchA> -- <更新过的文件>
git diff <BASE> <branchB> -- <更新过的文件>
```

输出下表，**每一项都必须有结论**：

| 分支 | 净增内容摘要 | 是否保留 | 位置 | 未保留原因（如有） |
|---|---|---|---|---|
| A | ... | ✅ / ❌ | file:line | — |
| B | ... | ✅ / ❌ | file:line | — |

**只要有 ❌，就必须暂停，逐项列给用户确认，禁止静默忽略。**

## 双向同步流程

```
阶段一（正向）：当前分支 = B
  AI  ：三方对比 → 双向融合 → 改写 B 的工作区文件 → 输出更新文件清单 + 漏删自检表
  用户：在 B 上 git add / commit / push

阶段二（反向）：用户手动切到 A
  AI  ：只针对阶段一更新过的文件，把已合并成果向 A 融合，逐块判定 + 漏删自检表
  用户：在 A 上 git add / commit / push
```

- 阶段一处理"当前分支 vs 另一分支"的全部差异，双向合并。
- 阶段二**只处理阶段一的更新文件清单**，避免带入无关改动。
- AI 在任一阶段都不切分支、不 commit、不 push，只改文件 + 给建议命令。
- 两个阶段都必须产出漏删自检表。

### 阶段一执行

1. 校验输入齐全，缺失则询问
2. `git branch --show-current` 确认当前分支（只读），全程不切换
3. 取 BASE（Step 0），拉两侧净增（Step 1）
4. 逐块分类 ①/②/③/④（Step 2）
5. 逐块融合：① 保留 A；② 保留 B；③ 双方拼接；④ 按 Step 3 取新并移植另一侧修复，无法判定则暂停
6. 改写工作区文件（Step 4）
7. 漏删自检（Step 5），有 ❌ 暂停等确认
8. 按「阶段输出模板」输出

### 阶段二执行

> ⚠️ 分支切换由**用户手动执行**，AI 绝不代劳。用户切好后再次调用本 Skill 并说明"执行反向同步"。

1. `git branch --show-current` 确认当前分支（只读）
2. 只读比较阶段一的更新文件清单：

   ```bash
   git diff <阶段一更新分支> <当前分支> -- <阶段一更新文件清单>
   ```

   把"阶段一已合并好的分支"作为一侧、当前分支作为另一侧，**对等合并**，不允许整段覆盖：
   - 当前分支相对阶段一分支独有的、非冲突改动 → 保留
   - 阶段一分支的改动 → 保留
   - 重叠冲突 → 按 Step 3 取新并移植另一侧修复

3. 逐块融合（规则同阶段一，尤其遵守六条红线）
4. 改写工作区文件
5. 漏删自检
6. 按「阶段输出模板」输出

### 阶段输出模板（两阶段共用）

**① 冲突与合并分析** — 基于 merge-base 的差异点；A、B 各自的修改意图；每个冲突块的分类；第 ④ 类的新旧判定依据；无法判定项列出两种方案与风险

**② 已写入的文件与改动摘要** — 文件路径 + 一句话说明，**必须写明保留了 A、B 各自哪些新增 / 修复**

**③ 漏删自检表（强制）** — 按 Step 5 表格，每项都要有结论

**④ 建议 Git 命令（仅供用户手动执行）**

> ⚠️ 以下命令仅为建议，AI 不执行任何 add / commit / push / merge / checkout 操作，也不自行切换分支。

```bash
git add <本次更新的文件>
git commit -m "chore: 合并 <branchA> 与 <branchB>，保留双方新增与修复，冲突按最新逻辑处理"
git push origin <当前分支>
```

**⑤ 本次更新文件清单**（供阶段二使用）— 逐行列出文件路径

## 停止条件

- 两个阶段都完成、漏删自检无 ❌ → 输出结果后停止
- 项目名或任一分支缺失 → 停止并询问补齐，不猜测推进
- 出现无法判定新旧的冲突，或漏删自检有 ❌ → 暂停，列方案等用户裁决
- 用户未切分支就要求执行阶段二 → 停止并提示先手动切分支

## 失败处理

- 工作区已有未提交改动 → 提示风险并暂停，不自行 stash / checkout / reset，等用户处置
- 目标路径不存在或读取失败 → 确认路径与大小写后重试一次，仍失败则记录并继续其余文件，最终报告列出失败清单
- 差异过多或文件过大超出单次处理能力 → 按文件 / 模块分批融合，每批独立出自检表并标注进度
- 写文件失败（权限 / 磁盘）→ 报告具体错误，未写入不得声称已融合
- 与用户给出的方向提示冲突 → 以逐块验证结果为准，把冲突点与判定依据列出请用户裁决

# Resume Tech Interview Decompose

将简历技术点拆解为结构化的面试准备内容：候选人能力四层模型 + 面试官七维提问框架。

## 适用场景

- 技术岗面试前，针对简历技术栈逐一突破准备
- 简历撰写时，校验技术点的深度是否匹配自身能力
- 面试官/技术面试官快速生成针对性面试题
- 模拟面试练习，自查技术盲区

## 核心方法论

### 候选人能力四层模型（从入门到精通）

1. **基础概念层**：技术定义、解决的核心痛点、适用场景、不适用场景、核心术语
2. **工程使用层**：常用 API/配置、项目集成方式、基础可运行实现
3. **故障调优层**：常见异常报错、排查思路、性能瓶颈、调优参数、典型踩坑案例
4. **底层原理层**：核心工作流程、关键实现机制、技术优缺点、同类技术对比与选型逻辑

> 标注「熟悉」需掌握前 3 层；标注「精通」需完整掌握 4 层并能结合项目案例阐述。

### 面试官七维提问框架

1. **概念理解类**：考察对技术边界的认知，而非死记定义
2. **核心原理类**：考察底层逻辑，是否知其所以然
3. **项目实战类**：考察真实落地经验，验证简历真实性
4. **配置 API 类**：考察实际编码经验，而非纸面理解
5. **故障调优类**：考察工程排错能力与问题解决思路
6. **对比选型类**：考察技术视野与方案决策能力
7. **延伸深挖类**：考察架构思维与技术上限

> **项目结合提问约束（必须遵守）**：上述七个维度中，**大部分维度的提问应结合简历中该技术点的项目使用场景即具体业务来设计**，而非脱离项目单独问八股。面试官最喜欢的问法是「你项目里用了 XXX，为什么这么选？遇到什么问题？怎么解决的？」而非「说一下 XXX 的原理」。具体规则见下方「项目结合提问约束」章节。

## 工作流程

1. 接收用户输入的技术点（支持单个或多个，以逗号/空格/换行分隔）
2. **版本时效性核查**：对每个技术点，确认其当前最新稳定版本（见下方「版本时效性约束规则」），后续所有 API 示例、配置写法、原理描述均以该版本为准
3. **项目结合核查**：检索简历/项目文档，确认该技术点是否在简历项目中出现过。若出现过，记录其项目使用场景与上下文，后续提问优先结合该项目场景设计
4. 对每个技术点，基于四层能力模型拆解候选人必备掌握内容
5. 基于七维提问框架，结合技术点特性与项目场景生成对应面试问题
6. 补充该技术点专属的高频深度问题与行业经典考点
7. 按统一格式结构化输出结果

## 版本时效性约束规则（必须遵守）

> **核心原则**：生成的所有技术拆解内容必须基于该技术点的**当前最新稳定版**。严禁使用已废弃或过时版本的 API、配置和概念。知识库中大量存在旧版本内容（尤其是快速迭代的技术如 LangChain、Elasticsearch、Spring Boot 等），必须主动甄别和排除。

### 强制约束

1. **版本基准线**：生成每个技术点的拆解内容前，必须基于下方「版本基准线表」确认该技术的当前最新稳定版。若表未收录，应联网查询最新稳定版后再生成内容。
2. **禁止过时 API**：不得使用已废弃版本的包名、导入路径、类名、方法签名或配置方式。例如 LangChain 0.1.x 的 `from langchain.chains import LLMChain` 在 1.x 已废弃，必须使用 `from langchain_core...` 或新的 LCEL 写法。
3. **禁止过时概念**：不得描述已在新版本中移除或改变的机制。例如 Elasticsearch 8.x 起已废弃 `RestHighLevelClient`，必须使用 `co.elastic.clients:elasticsearch-java` 新版客户端。
4. **版本演进标注**：当某技术点在版本间有重大变化（如 API 变更、架构重构）时，应在「底层原理层」或「故障调优层」明确标注版本差异，如「JDK8 vs JDK17 中 ConcurrentHashMap 的实现差异」。
5. **代码示例版本对齐**：所有代码片段必须与该技术点最新稳定版的 API 一致。若涉及不同版本写法差异，应在注释中标注 `// 旧版 (≤x.x)` 和 `// 新版 (≥x.x)`。
6. **已废弃技术显式标记**：对于被广泛使用但已废弃的内容（如 ES HLRC、Vue2、LangChain 0.x），必须在提及相关内容时标注 `[已废弃]`，并指出推荐替代方案。

## 项目结合提问约束（必须遵守）

> **核心原则**：面试官最喜欢「你项目里怎么用的 → 为什么这么选 → 遇到什么问题 → 怎么解决的」这条线，而非脱离项目单独问八股。因此，七维提问中大部分维度的问题必须结合简历中该技术点的项目使用场景来设计。

### 提问结合规则

1. **项目优先结合**：若该技术点在简历项目中出现过，则「项目实战」「配置与 API」「故障与调优」「对比选型」「延伸深挖」五个维度的问题**必须结合该项目场景**设计。例如简历写了用 Redis 做分布式锁，则故障调优维度应问「你项目里分布式锁遇到过什么问题？锁过期了怎么办？」而非泛泛问「Redis 死锁怎么解决？」
2. **概念理解与核心原理可脱离项目**：这两个维度可以单独问八股，考察对技术本身的认知。例如「Redis 为什么快？」「HashMap 的 put 流程是什么？」这类问题不需要绑定项目场景。
3. **项目未涉及的技术点**：若简历项目中完全没有使用该技术（如候选人简历没写 Kafka 但技能要求里列了），则七个维度均可按纯八股出题，但仍应设计「如果让你在项目中引入 XXX，你会怎么用」这类假设性问题。
4. **问题中应出现项目要素**：结合项目的问题应在题干中明确提及项目场景、业务背景或技术决策点，让候选人能回答「为什么」而不仅仅是「是什么」。例如：
   - ❌ 差：「说一下 ConcurrentHashMap 的原理」
   - ✅ 好：「你协同训练平台中用 ConcurrentHashMap 管理房间连接，为什么选它而不是 HashMap？并发下 size() 准确吗？」
   - ❌ 差：「Redis 缓存雪崩怎么解决」
   - ✅ 好：「你项目里用 Redis 做缓存，如果大量 key 同时过期怎么办？你怎么避免？」
5. **追问链设计**：每个维度的问题应可连环追问，形成「项目场景 → 技术选型原因 → 踩过的坑 → 优化方向」的深度考察链。

### 七维提问结合项目示例

以 Redis（简历中用于缓存、分布式锁、状态同步）为例：

- ✅ 项目实战：「你协同训练平台中 Redis 做了主载具选举，为什么用 Redis 而不用 ZooKeeper？选举机制的实现细节是什么？」
- ✅ 配置与API：「你项目里 Redis 的过期策略怎么配的？库存扣减用 Lua 脚本还是用 Redisson 的分布式锁？为什么？」
- ✅ 故障与调优：「速享外卖里 Lua 脚本扣库存，如果 Redis 宕机了怎么办？你有没有考虑过兜底方案？」
- ✅ 对比选型：「你项目里为什么选 Redis 做缓存而不是本地缓存（Caffeine）？两者怎么配合的？」
- ✅ 延伸深挖：「如果速享外卖的 QPS 翻 10 倍，你现有的 Redis 方案会出现什么瓶颈？你会怎么改？」

## 输出要求

- 每个技术点独立成段，批量输入时逐个输出
- 候选人应掌握内容：每层 3-6 条要点，简洁精准
- 面试官提问：每个维度 2-4 个问题，问题应具体、可追问、能区分深度
- 问题须结合该技术点的实际特性，避免泛泛而谈
- **大部分提问须结合简历项目场景**（见「项目结合提问约束」），纯八股仅限项目未涉及的技术点或概念理解/核心原理维度
- 底层原理层和延伸深挖类问题应体现行业经典考点和高频深度问题
- 输出语言：中文

## 使用示例

输入：`Redis`

输出（节选）：

### 技术点：Redis

> 版本基准：Redis Server 8.x · Jedis 6.x · Lettuce 6.x · Redisson 3.50.x（核查日期 2026-08-28）

#### 候选人应掌握内容

1. 基础概念层
   - 内存型 NoSQL 数据库，核心解决高并发下的数据访问性能问题
   - 适用场景：缓存、分布式锁、计数器、排行榜、会话存储、向量搜索（8.x 起内置）
   - 不适用场景：海量冷数据、强事务关系型数据
   - 核心术语：单线程模型、5 种基础数据结构、过期策略、Function（7.x 起替代部分 Lua 场景）
2. 工程使用层
   - 常用命令：set/get/expire/zadd/hset 等
   - Java 客户端：Jedis 6.x（统一连接池 API）、Lettuce 6.x（响应式）、Redisson 3.50.x（分布式对象）的基础使用
   - 集成 Spring Boot 3.x/4.x 的配置方式（`spring-boot-starter-data-redis`）
3. 故障调优层
   - 缓存三大问题：穿透、击穿、雪崩的成因与解决方案
   - 大 Key、热 Key 的识别与处理
   - 内存淘汰策略配置与调优
   - 持久化 RDB/AOF 的配置权衡（7.x 起支持多部分 AOF，4.x 单文件 AOF [已废弃]）
4. 底层原理层
   - 单线程 IO 多路复用模型为什么快（8.x 起部分命令支持多线程 I/O）
   - 主从复制、哨兵、集群的工作机制
   - Hash 槽分片原理与扩容流程
   - 与 Memcached 的核心差异

#### 面试官高频提问

1. 概念理解
   - Redis 主要解决什么问题？什么场景不适合用 Redis？
2. 核心原理
   - Redis 为什么快？单线程模型的优势是什么？
3. 项目实战
   - 你项目里用 Redis 做了什么？遇到过什么线上问题，怎么解决的？
   - 为什么项目选 Redis 而不用其他缓存方案？
4. 配置与API
   - 常用的过期策略有哪些？内存淘汰策略怎么配置？
5. 故障与调优
   - 缓存穿透、击穿、雪崩分别是什么，怎么解决？
   - 什么是大 Key，会带来什么问题，如何排查和处理？
6. 对比选型
   - Redis 和 Memcached 有什么区别？各自适用场景？
   - Jedis、Lettuce、Redisson 怎么选？
7. 延伸深挖
   - 如果并发量扩大 10 倍，Redis 缓存方案会出现什么问题，如何优化？
   - Redis 集群扩容的完整流程是什么？有哪些注意事项？

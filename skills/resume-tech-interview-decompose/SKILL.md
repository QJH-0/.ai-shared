# Resume Tech Interview Decompose

将简历技术点拆解为可直接用于面试的结构化内容：**速记表、双版本口述稿、痛点→方案→效果拆解、七维追问链、反向选型题、最佳实践对照与自评清单**。

不输出知识清单类内容（「应掌握的基础知识」之类的罗列）——要掌握什么，由提问和答案要点自然承载，避免产出大而记不住的八股清单。

## 核心方法论

### 面试官七维提问框架

概念理解、核心原理、项目实战、配置 API、故障调优、对比选型、延伸深挖。

面试官的主线是「项目里怎么用 → 为什么这么选 → 遇到什么问题 → 怎么解决」，而非脱离项目问八股。其中**项目实战、配置 API、故障调优、对比选型、延伸深挖五个维度的问题必须绑定简历项目场景**；概念理解与核心原理两维可纯八股。

绑定示例：

- ❌ 差：「说一下 ConcurrentHashMap 的原理」
- ✅ 好：「你项目里用 ConcurrentHashMap 管理并发连接，为什么选它而不是 HashMap？并发下 size() 准确吗？」

### 痛点驱动叙事（每个技术点的标准三段式）

1. **痛点**：原始方案的问题，有具体现象和数字（如原始 SQL 的 EXPLAIN 分析表、早期轮询方案的滞后/阻塞/误差）
2. **方案**：核心设计 + 关键数据结构 + 精简代码片段 + 逐层「为什么这样设计」
3. **效果**：优化前后量化对照表（响应时间、扫描方式、稳定性），拒绝无数字的「性能显著提升」

### 反向选型题

每个技术点至少设计 1 个「为什么不用 X」问题（为什么不用 Zookeeper/Redisson/窗口函数/原生 Netty/本地缓存……），考察技术视野与方案决策能力。答案要点应包含「X 的适用前提 + 本项目为何不满足该前提」。

### 行业最佳实践对照 + 诚实标注

将该技术点的实现对照业界标准方案，逐项标注：✅ 已做到（说明如何对应最佳实践）、⚠️ 未做到（如 fencing token、背压、锁续约）。未做到项不是缺陷，直接转化为「如果重新设计，你会怎么改进」的答案素材——主动坦白比被问穿体面得多。

## 工作流程

1. **接收输入**：技术点（单个或多个）。若用户提供了简历/项目文档，提取该技术点的项目上下文：项目名称、业务背景、具体用法、架构角色、与其他技术的配合关系；未提供则询问，用户仍不提供则按纯八股模式生成假设性项目问题。
2. **版本核查**：对每个技术点联网确认当前最新稳定版，输出中标注版本基准与核查日期。禁止过时 API 与已废弃概念（如 ES `RestHighLevelClient`、LangChain 0.x 旧路径）；版本间有重大变化时显式标注差异（如「JDK8 vs JDK17 的 ConcurrentHashMap」）。
3. **识别标注**：按「了解/熟悉/精通」校准提问深度与追问强度。
4. **结构化输出**：按下方输出结构生成。

## 输出结构

```markdown
# XXX — 面试准备

> 核查日期 YYYY-MM-DD

## 一、速记表

| 技术点/功能点 | 核心方案 | 关键指标 |
|---|---|---|
（一行一个，面试前 5 分钟扫一遍）

## 二、面试口述稿

### 1 分钟极简版
> 第一人称、可直接背诵，一段话串起所有技术点各一句话

### 3 分钟完整版
> 按技术点分块，每块标注建议时长（如「约 30 秒」），每块按「痛点一句 → 方案两句 → 效果一句」组织

## 三、技术点：XXX

> 版本基准：XXX vX.x · 核查日期 YYYY-MM-DD
> 项目场景：（简历提取的使用场景摘要，未涉及则写"简历项目未涉及"）

### 痛点 → 方案 → 效果
- 原始痛点（现象 + 数字）
- 核心方案（关键数据结构 + 精简代码片段）
- 为什么这样设计（逐层原理）
- 效果量化对照表（优化前 vs 优化后）
- **一句话总结**（可直接背诵）

### 七维提问（含追问链与具体答案）
每维 2-4 个问题；每维至少 1 条追问链，高权重维度（项目实战、故障调优、延伸深挖）可 2 条。追问链模式：
项目场景切入 → 深入原理/选型原因 → 故障/边界/性能 → 优化/扩展/架构演进

### 反向选型题
- 「为什么不用 X」≥ 1 个，附答案要点

### 行业最佳实践对照
业界方案 vs 本项目实现，✅/⚠️ 逐项标注；⚠️ 项汇总为「如果重新设计的改进方向」

### 自评清单
- [ ] 能否说出 3 个适用场景和 2 个不适用场景？
- [ ] 能否说出最常用的 5 个 API/配置？
- [ ] 能否描述 2 个常见故障的排查思路？
- [ ] 能否说清核心工作流程的关键步骤？
- [ ] 能否结合项目回答"为什么选它？遇到什么问题？怎么解决的？"
- [ ] 能否回答"如果 QPS/数据量翻 10 倍，现有方案的瓶颈和改进？"
```

## 自评清单设计规则

每条为封闭问题「能否…？」，用「能/不能/不确定」自检；覆盖常用使用与底层原理各至少 1 条、项目结合至少 1 条、扩展性（容量/并发翻倍推演）至少 1 条。清单末尾提示：3 条以上"不能/不确定"，优先复习该技术点。

## 边界情况

- **非框架类技术点**（设计模式、算法、协议）：提问侧重编码实现、边界条件与复杂度分析，而非运维排错；版本约束放宽。
- **新技术/新版本**（发布不足 6 个月）：标注「生产案例较少」，提问侧重原理与设计意图，线上故障案例不足的维度降权。
- **技术点过宽**（如"Java""数据库"）：先提示细化为子领域（如"Java 并发""索引优化"），用户坚持则按全景概览组织，侧重宏观认知与选型。
- **简历未涉及的技术点**：项目场景行标注「假设性提问」，增加「如果让你在现有项目中引入 XXX，怎么设计？」类问题，自评清单相应增加引入方案设计能力自检。

## 输出要求

- 每个技术点独立成段，批量输入逐个输出；输出语言中文。
- 口述稿必须第一人称、口语化、可直接背诵，禁用要点罗列体。
- 所有效果描述尽量带数字；无真实数据时标注「示例数字，按实际情况替换」。
- 问题须结合技术点实际特性，避免泛泛而谈；绑定项目场景的维度不得退化为纯八股。
- 核心原理与延伸深挖维度体现行业经典考点和高频深度问题。
- 不输出「应掌握的基础知识」类清单；知识覆盖由提问与答案要点承载，总量以候选人能背下为准。

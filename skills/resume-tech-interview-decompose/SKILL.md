# Resume Tech Interview Decompose

将简历技术点拆解为可直接用于面试的内容。文档主体形态:**以「技术点的问题及其延展」为小标题,每个问题给出深度论述答案——完整原理拆解 + 代码示例 + 必要时 mermaid 图解**。

一句话产出标准:**宁深勿多**。每个技术点收敛为 5-8 个核心问题,每个问题答透;任何"两三句话就结束"的答案都视为不合格产出,必须继续挖深或补充代码。

## 核心方法论

### 问题及延展组织法

不按维度框架分类问题。每个技术点直接列 **5-8 个核心问题**作为三级小标题,每个核心问题后跟 **1-2 个延展追问**(面试官听完答案后最可能接着问的问题)。

**问题清单设计自查**(设计问题时逐项核对,不作为分类输出):

- 至少 2 个项目实战问题(项目里怎么用 / 为什么这么选 / 遇到什么问题怎么解决)
- 至少 2 个核心原理问题(该技术点行业最高频的深度原理)
- 至少 1 个反向选型问题(「为什么不用 X」——X 的适用前提 + 本项目为何不满足)
- 至少 1 个故障排查或性能调优问题(必须绑定项目场景)
- 至少 1 个延展深挖问题(QPS / 数据量翻 10 倍,现有方案的瓶颈与演进)

简历提供了项目上下文时,项目实战、故障调优、反向选型类问题必须绑定场景:

- ❌ 差:「说一下 ConcurrentHashMap 的原理」
- ✅ 好:「你项目里用 ConcurrentHashMap 管理并发连接,为什么选它而不是对 HashMap 加锁?并发场景下 size() 的值准确吗?」

### 深度答案标准(强制,防止退化为两三句话)

每个核心问题的答案由以下模块按需组合,**结论与原理展开为必有模块**:

1. **结论**——2-3 句可直接说出口的面试开场话术,先给答案再展开。
2. **原理展开**——完整段落论述,是答案的主体:
   - 讲清机制链条:数据结构如何变化、状态如何流转、请求走什么路径,逐层回答「为什么这样设计」
   - 必须落到具体条件与数字(如「链表长度 > 8 且数组长度 ≥ 64 才树化,阈值选 8 源自泊松分布下链表长度达到 8 的概率约亿分之六」),禁止「用了 XX 机制保证了高性能」式的空话
   - 篇幅基准:正文 300-600 字;不足 200 字说明没答透,继续往下挖一层
   - 短段落：单个段落不超过 5～7 行（约 150～200 字），需换行或分点的地方必须分段。
   - 结构化：超过 3 个并列项或流程步骤，必须使用列表（有序/无序）。
3. **代码示例**——核心问题必配,按问题选形态:
   - 项目场景代码(按简历项目上下文改写的真实用法)
   - 框架源码走读(JDK / Redis / Netty 等关键片段,标注来源版本)
   - 配置 / SQL / 命令
   - 要求:10-40 行、真实 API 不虚构、关键行注释写「为什么」而非复述「是什么」
4. **边界与陷阱**——多数问题应有:什么条件下结论不成立、常见误区、生产事故模式(如「主从延迟窗口内读从库会读到旧值」)。
5. **图解**——必要时,判定规则:
   - **必须配图**:流程与时序类(一次写请求的完整链路)、架构拓扑类(分层 / 集群 / 分片)、数据结构与状态机类(B+ 树、线程池状态流转、TCP 状态机)
   - **不硬配图**:纯概念辨析、参数对比类问题,文字说得更清楚就不要图
   - 形式:mermaid(flowchart / sequenceDiagram / stateDiagram-v2 / classDiagram),单图节点 ≤ 15,一张图讲一件事,图后必须跟 2-3 句文字解读;复杂图可参考 `C:\Users\20448\.ai-shared\skills\mermaid-master`
6. **延展解答**——延展追问紧跟核心答案之后作答,同样完整论述(篇幅可短于核心答案,但禁止只列问题不答或要点式敷衍)。

**好 / 差答案对照**(锚定「深度」的含义):

- ❌ 差(两句话,无机制、无代码):「为什么用 Redis 分布式锁?——用 SET NX 保证互斥,加过期时间防死锁,值存唯一 ID 防误删。」
- ✅ 好(节选):结论给出 SET key value NX PX ttl 的原子性来源(Redis 单线程命令执行)→ 原理展开讲为什么 SETNX 与 EXPIRE 分开执行会在客户端崩溃后留下永不过期的 key、误删场景为什么必须用 Lua 脚本「先比对 value 再删除」保证原子、锁续期看门狗的周期与续期窗口如何配合 → 代码给出加锁 Lua 脚本与释放脚本的完整实现 → 边界讲主从切换导致的锁丢失与 RedLock 的争议 → 延展追问「Redisson 的看门狗默认 30s 锁、10s 续一次,为什么这样设计」。

### 痛点驱动叙事(项目实战类答案的骨架)

项目实战问题的答案按三段组织,数字贯穿始终:

1. **痛点**:原始方案的问题,有具体现象和数字(如原始 SQL 的 EXPLAIN 全表扫描行数、轮询方案的延迟与无效请求量)
2. **方案**:核心设计 + 关键数据结构 + 代码片段 + 逐层「为什么这样设计」
3. **效果**:优化前后量化对照表(响应时间、扫描方式、稳定性),拒绝无数字的「性能显著提升」

### 行业最佳实践对照 + 诚实标注

将该技术点的实现对照业界标准方案,逐项标注:✅ 已做到(如何对应最佳实践)、⚠️ 未做到(如 fencing token、背压、锁续约)。⚠️ 项直接转化为「如果重新设计,你会怎么改进」的答案素材——主动坦白比被问穿体面得多。

## 工作流程

1. **接收输入**:技术点(单个或多个)。若用户提供了简历 / 项目文档,提取该技术点的项目上下文:项目名称、业务背景、具体用法、架构角色、与其他技术的配合关系;未提供则询问,用户仍不提供则按纯八股模式生成假设性项目问题。
2. **版本核查**:对每个技术点联网确认当前最新稳定版,输出中标注版本基准与核查日期。禁止过时 API 与已废弃概念(如 ES `RestHighLevelClient`、LangChain 0.x 旧路径);版本间有重大变化时显式标注差异(如「JDK8 vs JDK17 的 ConcurrentHashMap」)。源码走读类答案必须标注所引源码的版本。
3. **识别标注**:按简历中「了解 / 熟悉 / 精通」校准挖深层级——「精通」挖到源码与设计取舍,「熟悉」挖到机制链条,「了解」侧重适用场景与选型逻辑。
4. **结构化输出**:按下方输出结构生成,输出前执行「反退化自检」。

## 反退化自检(输出前逐问题核对)

- [ ] 原理展开正文是否 ≥ 300 字,且含具体机制、条件或数字,而非空泛断言?
- [ ] 删掉代码后,答案是否仍是完整段落论述,而非要点罗列?
- [ ] 核心问题是否配了 10 行以上的真实代码示例(源码走读已标注版本)?
- [ ] 流程 / 时序 / 架构 / 数据结构类问题是否配了 mermaid 图,图后是否有解读?
- [ ] 每个延展追问是否都有完整解答,而不是只列问题?
- [ ] 面试官听完答案最可能的下一个追问,是否已吸收进答案或转为延展问题?
- [ ] 问题总数是否控制在 5-8 个?若超了,优先合并相近问题而非砍深度。

## 边界情况

- **非框架类技术点**(设计模式、算法、协议):问题侧重编码实现、边界条件与复杂度分析;代码示例为手写实现与复杂度对照,配图侧重数据结构与状态流转;版本约束放宽。
- **新技术 / 新版本**(发布不足 6 个月):标注「生产案例较少」,问题侧重原理与设计意图,避免编造线上故障案例。
- **技术点过宽**(如"Java""数据库"):先提示细化为子领域(如"Java 并发""索引优化"),用户坚持则按全景概览组织,侧重宏观认知与选型。
- **简历未涉及的技术点**:项目场景行标注「假设性场景」,增加「如果让你在现有项目中引入 XXX,怎么设计?」类问题,其答案按完整方案设计作答(架构图 + 关键代码),不得敷衍。

## 输出要求

- 每个技术点独立成段,批量输入逐个输出;输出语言中文。
- 口述稿必须第一人称、口语化、可直接背诵,禁用要点罗列体。
- 所有效果描述尽量带数字;无真实数据时标注「示例数字,按实际情况替换」。
- 代码示例语言跟随技术点(Java / SQL / YAML / Shell 等);禁止虚构不存在的 API。
- 深度优先于数量:宁可 5 个问题每个 500 字 + 代码 + 图,不要 20 个问题每个两三句。
- 不输出「应掌握的基础知识」类清单;知识覆盖由问题与深度答案承载。

# Resume Tech Interview Decompose

将简历技术点拆解为结构化的面试准备内容：候选人能力四层模型 + 面试官七维提问框架 + 追问链 + 参考答案要点 + 候选人自评清单。

## 适用场景

- 技术岗面试前，针对简历技术栈逐一突破准备
- 简历撰写时，校验技术点的深度是否匹配自身能力
- 面试官/技术面试官快速生成针对性面试题
- 模拟面试练习，自查技术盲区
- 技术栈复习，系统梳理某个技术的知识体系

## 核心方法论

### 候选人能力四层模型（从入门到精通）

1. **基础概念层**：技术定义、解决的核心痛点、适用场景、不适用场景、核心术语
2. **工程使用层**：常用 API/配置、项目集成方式、基础可运行实现
3. **故障调优层**：常见异常报错、排查思路、性能瓶颈、调优参数、典型踩坑案例
4. **底层原理层**：核心工作流程、关键实现机制、技术优缺点、同类技术对比与选型逻辑

> 简历标注「了解」需掌握第 1 层 + 第 2 层基础；标注「熟悉」需掌握前 3 层；标注「精通」需完整掌握 4 层并能结合项目案例阐述。根据简历中的标注程度，调整各层要点的详略级别。

### 面试官七维提问框架

1. **概念理解类**：考察对技术边界的认知，而非死记定义
2. **核心原理类**：考察底层逻辑，是否知其所以然
3. **项目实战类**：考察真实落地经验，验证简历真实性
4. **配置 API 类**：考察实际编码经验，而非纸面理解
5. **故障调优类**：考察工程排错能力与问题解决思路
6. **对比选型类**：考察技术视野与方案决策能力
7. **延伸深挖类**：考察架构思维与技术上限

> 面试官最喜欢「你项目里怎么用的 → 为什么这么选 → 遇到什么问题 → 怎么解决的」这条线，而非脱离项目单独问八股。七个维度中，大部分维度的提问应结合简历中该技术点的项目使用场景设计。具体规则见「项目结合提问约束」章节。

## 工作流程

1. **接收输入**：接收用户输入的技术点（支持单个或多个，以逗号/空格/换行分隔）。若用户同时提供了简历或项目文档，优先从文档中提取项目上下文。
2. **简历项目上下文提取**：若用户提供了简历/项目文档，检索该技术点在简历中的出现位置，记录其：项目名称、业务场景、具体用法、架构角色、与其他技术的配合关系。这些上下文将注入后续提问设计。若未提供简历文档，向用户询问是否需要提供以获得更精准的项目结合提问；用户未提供则按纯八股模式生成，但仍应设计假设性项目问题。
3. **版本时效性核查**：对每个技术点，确认其当前最新稳定版本（见「版本时效性约束规则」），后续所有 API 示例、配置写法、原理描述均以该版本为准。
4. **能力标注识别**：若简历中对该技术点有"了解/熟悉/精通"标注，据此调整四层模型各层的详略程度。
5. **四层模型拆解**：对每个技术点，基于四层能力模型拆解候选人必备掌握内容。
6. **七维提问生成**：基于七维提问框架，结合技术点特性与项目场景生成对应面试问题，并为每个维度设计追问链。
7. **参考答案要点**：为每个提问提供简明的参考答案要点（关键词级别，非完整答案），帮助候选人快速自查。
8. **专属深度问题补充**：补充该技术点专属的高频深度问题与行业经典考点。
9. **自评清单生成**：生成该技术点的候选人自评清单，标注重点盲区。
10. **结构化输出**：按统一格式输出全部结果。

## 版本时效性约束规则

> 生成的所有技术拆解内容必须基于该技术点的**当前最新稳定版**。知识库中大量存在旧版本内容（尤其是快速迭代的技术如 LangChain、Elasticsearch、Spring Boot 等），必须主动甄别和排除。过时的 API 和概念会误导候选人，这是本技能的红线。

### 强制约束

1. **版本基准线**：生成每个技术点的拆解内容前，必须确认该技术的当前最新稳定版。优先查阅下方「常见技术版本基准线表」；若表未收录或表中版本可能已过时（表末核查日期距今超过 3 个月），必须联网查询最新稳定版后再生成内容。
2. **禁止过时 API**：不得使用已废弃版本的包名、导入路径、类名、方法签名或配置方式。例如 LangChain 0.1.x 的 `from langchain.chains import LLMChain` 在 1.x 已废弃，必须使用 `from langchain_core...` 或新的 LCEL 写法。
3. **禁止过时概念**：不得描述已在新版本中移除或改变的机制。例如 Elasticsearch 8.x 起已废弃 `RestHighLevelClient`，必须使用 `co.elastic.clients:elasticsearch-java` 新版客户端。
4. **版本演进标注**：当某技术点在版本间有重大变化（如 API 变更、架构重构）时，在「底层原理层」或「故障调优层」明确标注版本差异，如「JDK8 vs JDK17 中 ConcurrentHashMap 的实现差异」。
5. **代码示例版本对齐**：所有代码片段必须与该技术点最新稳定版的 API 一致。若涉及不同版本写法差异，在注释中标注 `// 旧版 (≤x.x)` 和 `// 新版 (≥x.x)`。
6. **已废弃技术显式标记**：对于被广泛使用但已废弃的内容（如 ES HLRC、Vue2、LangChain 0.x），在提及相关内容时标注 `[已废弃]`，并指出推荐替代方案。

## 项目结合提问约束

> **核心原则**：面试官最喜欢「你项目里怎么用的 → 为什么这么选 → 遇到什么问题 → 怎么解决的」这条线，而非脱离项目单独问八股。七维提问中大部分维度的问题必须结合简历中该技术点的项目使用场景来设计。这样能验证简历真实性，也能考察候选人的深度理解。

### 简历项目上下文提取

当用户提供简历或项目文档时，对每个技术点执行以下提取：

1. **定位**：在简历/项目文档中搜索该技术点的出现位置
2. **提取项目要素**：
   - 项目名称与业务背景（如"多智能体深度研报助手"）
   - 该技术在项目中的具体用途（如"Redis 用于热数据缓存与会话持久化"）
   - 架构角色（如"作为三层记忆系统的热缓存层"）
   - 与其他技术的配合关系（如"Redis + PostgreSQL + Milvus 构成异构记忆架构"）
   - 涉及的关键实现细节（如"两级语义缓存 L1 Milvus + L2 Redis"）
3. **注入提问**：将提取的项目要素融入问题题干，使问题具有项目场景绑定

### 提问结合规则

1. **项目优先结合**：若该技术点在简历项目中出现过，则「项目实战」「配置与 API」「故障与调优」「对比选型」「延伸深挖」五个维度的问题**必须结合该项目场景**设计。例如简历写了用 Redis 做分布式锁，则故障调优维度应问「你项目里分布式锁遇到过什么问题？锁过期了怎么办？」而非泛泛问「Redis 死锁怎么解决？」
2. **概念理解与核心原理可脱离项目**：这两个维度可以单独问八股，考察对技术本身的认知。例如「Redis 为什么快？」「HashMap 的 put 流程是什么？」这类问题不需要绑定项目场景。
3. **项目未涉及的技术点**：若简历项目中完全没有使用该技术（如候选人简历没写 Kafka 但技能要求里列了），则七个维度均可按纯八股出题，但仍应设计「如果让你在项目中引入 XXX，你会怎么用」这类假设性问题，考察候选人的技术规划能力。
4. **问题中应出现项目要素**：结合项目的问题应在题干中明确提及项目场景、业务背景或技术决策点，让候选人能回答「为什么」而不仅仅是「是什么」：
   - ❌ 差：「说一下 ConcurrentHashMap 的原理」
   - ✅ 好：「你项目中用 ConcurrentHashMap 管理并发连接，为什么选它而不是 HashMap？并发下 size() 准确吗？」
   - ❌ 差：「Redis 缓存雪崩怎么解决」
   - ✅ 好：「你项目里 Redis 做热缓存，如果大量 key 同时过期怎么办？你怎么避免？」
5. **追问链设计**：每个维度的问题应可连环追问，形成「项目场景 → 技术选型原因 → 踩过的坑 → 优化方向」的深度考察链。每个维度至少设计一条追问链。

### 追问链设计规则

追问链模拟面试官的连环提问，帮助候选人预判深度追问方向。每条追问链遵循以下模式：

```
起始问题（项目场景绑定）
  → 追问1（深入原理/选型原因）
    → 追问2（故障/边界/性能）
      → 追问3（优化/扩展/架构演进）
```

追问链的设计要点：
- 起始问题从项目场景切入，降低防线
- 每次追问逼近一个「说不出来」的边界，帮助候选人定位盲区
- 追问链不是要难倒候选人，而是帮助候选人预判面试官会往哪个方向深挖
- 每个维度至少 1 条追问链，高权重维度（项目实战、故障调优、延伸深挖）可设计 2 条

### 七维提问结合项目示例

以 Redis 为例（假设简历中用于：多智能体系统的热缓存、两级语义缓存 L2 层、会话持久化、分布式状态同步）：

- ✅ 项目实战：「你 CloudAgent 项目中 Redis 做了热缓存和会话持久化，为什么选 Redis 而不用本地缓存（Caffeine）？」→ 追问：「热缓存丢了怎么办？你提到 Redis 丢失可从 PG 重建，重建流程是什么？」
- ✅ 配置与API：「你两级语义缓存中 L2 是 Redis 精确匹配，缓存的数据结构是什么？过期策略怎么配的？」→ 追问：「Scope 隔离 public/user 是怎么实现的？key 命名规则是什么？」
- ✅ 故障与调优：「你项目里 Redis 和 PG 做 AP 最终一致性，如果 Redis 宕机了怎么办？恢复后数据不一致怎么处理？」→ 追问：「有没有考虑过 Redis 集群方案？哨兵和 Cluster 你会怎么选？」
- ✅ 对比选型：「你 DeepResearch 项目用 PG+Redis+Milvus 三层记忆，CloudAgent 也是类似架构，为什么两个项目都选 Redis？有没有考虑过用 Memcached 替代？」
- ✅ 延伸深挖：「如果 CloudAgent 的 QPS 翻 10 倍，你现有的两级缓存方案会出现什么瓶颈？你会怎么改？」→ 追问：「L1 Milvus 向量匹配的余弦距离 ≤ 0.08 这个阈值，QPS 上去后还合理吗？」

## 候选人自评清单设计规则

自评清单的目的是帮助候选人快速定位盲区，设计要点：

1. **每条为一个可自检的封闭问题**，以「能否…？」开头，候选人用「能/不能/不确定」回答
2. **覆盖四层模型的各层**：基础概念、工程使用、故障调优、底层原理各至少 1 条
3. **包含项目结合自检**：至少 1 条关于项目场景的回答能力
4. **包含扩展性自检**：至少 1 条关于高并发/架构演进的思考能力

## 边界情况处理

### 1. 非框架类技术点

对于设计模式、数据结构、算法、网络协议等非框架类技术点：
- 四层模型仍然适用，但侧重调整：「工程使用层」侧重编码实现而非配置；「故障调优层」侧重边界条件与性能分析而非运维排错
- 版本时效性约束可放宽（概念本身相对稳定），但若涉及语言标准库实现差异仍需标注版本

### 2. 新兴技术或刚发布的新版本

对于发布不到 6 个月的新技术或新版本：
- 在版本基准行标注「（新发布，生产案例较少）」
- 提问侧重概念理解和原理设计意图，而非故障调优（线上案例不足）
- 在延伸深挖维度考察候选人对技术发展趋势的判断力

### 3. 技术点过于宽泛

若用户输入的技术点过于宽泛（如"Java""Python""数据库"）：
- 主动提示用户细化为子领域（如"Java 并发""Python 异步""数据库索引优化"）
- 若用户确认要按宽泛技术点处理，则四层模型按该技术的全景概览组织，提问侧重宏观认知与选型

### 4. 技术点不在简历中但用户要求准备

若用户明确要求准备简历中未出现的技术点：
- 在项目场景行标注「简历项目未涉及，以下为假设性提问」
- 七维提问中增加「如果让你在项目中引入 XXX，你会怎么设计？」类假设性问题
- 自评清单增加「能否设计一个将该技术引入现有项目的方案？」

#### 一、候选人应掌握内容

1. 基础概念层
   - 内存型 NoSQL 数据库，核心解决高并发下的数据访问性能问题
   - 适用场景：缓存、分布式锁、计数器、排行榜、会话存储、向量搜索（8.x 起内置）
   - 不适用场景：海量冷数据、强事务关系型数据
   - 核心术语：单线程模型、5 种基础数据结构、过期策略、Function（7.x 起替代部分 Lua 场景）
2. 工程使用层
   - 常用命令：set/get/expire/zadd/hset 等
   - Java 客户端：Jedis 6.x（统一连接池 API）、Lettuce 6.x（响应式）、Redisson 3.50.x（分布式对象）
   - 集成 Spring Boot 3.x/4.x 的配置方式（`spring-boot-starter-data-redis`）
   - Python 客户端：redis-py 5.x（异步支持 `redis.asyncio`）
3. 故障调优层
   - 缓存三大问题：穿透、击穿、雪崩的成因与解决方案
   - 大 Key、热 Key 的识别与处理
   - 内存淘汰策略配置与调优
   - 持久化 RDB/AOF 的配置权衡（7.x 起支持多部分 AOF，4.x 单文件 AOF [已废弃]）
4. 底层原理层
   - 单线程 IO 多路复用模型为什么快（8.x 起部分命令支持多线程 I/O）
   - 主从复制、哨兵、集群的工作机制
   - Hash 槽分片原理与扩容流程
   - 与 Memcached 的核心差异

#### 二、面试官高频提问（含追问链与参考答案要点）

1. 概念理解
   - **问题**：Redis 主要解决什么问题？什么场景不适合用 Redis？
     - 参考答案要点：内存加速、降低 DB 压力、不适合强事务/海量冷数据
   - **追问链**：为什么不适合强事务 → 如果必须用 Redis 做事务呢 → Redis 事务和 MySQL 事务的本质区别

2. 核心原理
   - **问题**：Redis 为什么快？单线程模型的优势是什么？
     - 参考答案要点：内存操作、IO 多路复用、无锁无上下文切换、8.x 多线程 I/O 仅用于读写 socket
   - **追问链**：单线程为什么够用 → 8.x 为什么要引入多线程 I/O → 多线程 I/O 会带来线程安全问题吗

3. 项目实战
   - **问题**：你 CloudAgent 项目中 Redis 做了热缓存和会话持久化，为什么选 Redis 而不用本地缓存（Caffeine）？
     - 参考答案要点：多实例共享状态、缓存一致性、会话跨实例可用、AP 最终一致性
   - **追问链**：为什么不用 Caffeine → 多实例本地缓存怎么同步 → Redis 丢失可从 PG 重建，重建流程是什么 → 重建期间请求怎么处理
   - **问题**：你提到两级语义缓存 L2 是 Redis 精确匹配，缓存的数据结构是什么？Key 命名规则？
     - 参考答案要点：String/Hash 存 Q&A、Scope 隔离 public/user、key 含 scope 前缀

4. 配置与API
   - **问题**：你项目里 Redis 的过期策略怎么配的？内存淘汰策略选的什么？为什么？
     - 参考答案要点：allkeys-lru / volatile-lru、TTL 设置、过期策略 passive + active
   - **追问链**：为什么选这个淘汰策略 → 换成 LFU 会怎样 → 如何监控淘汰策略是否有效

5. 故障与调优
   - **问题**：你项目里 Redis 和 PG 做 AP 最终一致性，如果 Redis 宕机了怎么办？恢复后数据不一致怎么处理？
     - 参考答案要点：降级直查 PG、异步重建缓存、延迟双删、最终一致性窗口
   - **追问链**：Redis 宕机期间请求怎么处理 → 恢复后是全量重建还是增量 → 重建期间旧脏数据怎么清理
   - **问题**：什么是大 Key？你项目里有没有大 Key 风险？怎么排查和处理？
     - 参考答案要点：redis-cli --bigkeys、拆分 Hash、异步删除 UNLINK

6. 对比选型
   - **问题**：你两个项目都用 Redis 做缓存，有没有考虑过用 Memcached 替代？为什么选 Redis？
     - 参考答案要点：数据结构丰富、持久化支持、集群原生支持、Memcached 纯 KV
   - **追问链**：Memcached 什么场景比 Redis 好 → 如果只需要纯 KV 缓存 → 性能差异有多大

7. 延伸深挖
   - **问题**：如果 CloudAgent 的 QPS 翻 10 倍，你现有的两级缓存方案会出现什么瓶颈？你会怎么改？
     - 参考答案要点：L1 Milvus 向量计算瓶颈、Redis 单节点内存/连接数瓶颈、读写分离、Cluster 分片
   - **追问链**：L1 向量匹配瓶颈怎么解决 → Redis Cluster 分片后语义缓存怎么跨节点 → 是否考虑引入本地缓存做 L0

# 借鉴型计划的前提核实

## 适用场景

用户给出一份从**另一个项目**类推而来的优化/重构计划（常见措辞：「参考 X 项目的做法」「借鉴 Y 的这几条」），要求逐条实施。也适用于评审自己早先写的计划。

**不要直接开工。** 先花 10 分钟核实每条措施的前提。原计划的作者是照着源项目的架构写的，目标项目的架构未必有对应对象。

## 为什么必须核实：本次实测结果

某次 6 批次计划中，**至少 6 条措施的前提不成立**（源项目把产物存表、逐页生成；目标项目把产物存在 checkpoint 里）：

| 计划条目 | 核实结果 |
| --- | --- |
| 全局并发上限（Semaphore） | 图里唯一并行只有 2 个节点，且两节点内部检索是顺序执行 → 无可触发场景 |
| 单点重试与全量重跑同路径 | 代码里**没有任何节点级重试** → 无可统一的对象 |
| 确定性章节配额（position 取模） | 目标项目是**单次调用生成整篇**，没有「各章独立生成单元」的结构 |
| 输入指纹 `input_signature` | 全库无产物表 → 没有可标记 stale 的行 |
| 条件更新 `expected_revision` | 有载体但语义相反：写入全是「最后写入胜出」的元数据，加乐观锁会让**异步写**间歇失败 |
| 幂等键 | **已实现**（消费侧闸门 + `ON CONFLICT DO UPDATE`）→ 重复劳动 |

若照原计划实施，会写出「给不存在的表加列」「给不需要锁的数据加锁」「重复实现已有幂等」三类无效改动。

## 核实清单（按顺序，每条都有对应命令）

### 1. 措施提到的**配置项/字段**是否真被消费

最常见的断链：定义、映射、文档都齐，但**全项目无人读取**，改动它没有任何效果。

```bash
# 用字段名 grep 全部生产代码（排除测试与缓存）
grep -rn "字段名" app/ --include=*.py | grep -v __pycache__ | grep -v "^app/test"
```

判据：**出现次数 ≤ 2（定义处 + 映射处）即为死配置**。本次实测中 `node_models`、`enable_milvus` 都是这一类，且都是「配置项承诺的能力从未兑现」。

### 2. 措施提到的**机制/对象**是否真存在

```bash
# 表结构
grep -rn "CREATE TABLE" app/ --include=*.py
# 并发原语（判断「并发上限」类措施有无对象）
grep -rn "asyncio.gather\|Semaphore\|create_task\|TaskGroup" app/ --include=*.py
# 重试机制
grep -rn "retry\|max_attempts\|RetryPolicy" app/ --include=*.py
```

### 3. 措施假设的**调用形态**是否成立

例如「各章由不同生成单元产出，需配额协调」——去读那个函数：

```bash
grep -n "astream\|ainvoke\|for section\|for page" <目标文件>
```

若是单次调用生成整体，则「配额协调」类措施无对象，真实问题多半在别处（本次发现真实根因是**提示词没把大纲传下去**，属断链而非并发）。

### 4. 措施提到的**生成物**是否有对拍/新鲜度断言

```bash
# 找生成器与其产物
ls scripts/ | grep -i export
# 产物是否被任何测试引用
grep -rn "<产物文件名>" app/test/ agent_front/test/
```

若产物是手工维护的（生成器只产出中间格式），则「前后端类型不一致」不会被编译期或运行期捕获 → 这是**真缺口，值得补断言**。

### 5. 跨边界传递的**响应头/字段**是否真的可达

最常见的静默失效：后端在发，前端收不到。

```bash
# 自定义响应头 + CORS 是否 expose（跨域时未 expose 的响应头对 JS 不可见）
grep -rn "expose_headers\|allow_origins" app/ --include=*.py
```

本次实测：后端用 `X-Report-Warnings` 回传报告质量提醒，但 CORS 只配了 `allow_origins` 没配 `expose_headers` → **跨域部署下前端永远读不到**，warning 被静默丢弃。

同类检查：跨进程/跨语言边界的字段（SSE 事件名、MQ 消息字段、gRPC 字段号）都要确认**两侧都有对应的读/写代码**，而不只是定义存在。

## 断链速查表（同类问题在单个项目里反复出现，值得逐条 grep）

| 断链类型 | 症状 | 核实命令 | 判据 |
| --- | --- | --- | --- |
| 死配置 | 配置项定义了但无人读，改了没效果 | `grep -rn "<字段名>" app/ --include=*.py \| grep -v test` | 出现次数 ≤2（定义+映射） |
| 生成物漂移 | 生成器只产中间格式，最终产物手工维护 | `grep -rn "<产物名>" app/test/` | 无任何断言引用 |
| 开关失效 | 开关存在但未接入分支，关掉仍走原路径 | 同「死配置」 | 同上 |
| 响应头不可达 | 后端在发，跨域时 JS 读不到 | `grep -rn "expose_headers" app/` | 未列出该头 |
| 字段单侧存在 | 事件/MQ 字段只有一侧读写 | 两侧各 grep 一次字段名 | 任一侧为空 |

## 产出要求

1. **不做的条目必须写明理由与证据**（命令 + 观察结果），写进计划文档的对应批次下。
2. **改目标的条目要说清原目标为何不成立、真实根因是什么**。本次把「加章节配额」改为「修大纲断链」，修出的是用户可见问题。
3. 核实过程中发现的**断链缺陷**（配置无人读、生成物无对拍）优先修 —— 它们是真实缺陷，且往往比原计划条目价值更高。

## 反面教训（不要这样做）

- ❌ 因为计划写了就照做，把「无触发场景的基础设施」也建起来。它会变成无人维护的死代码。
- ❌ 用「按经验设个默认值」代替核实。本次看门狗默认值（900s）就是照旧模型估的，切模型后已不适用 —— 正确做法是**补上标定所需的观测信息**，而不是猜一个新数字。
- ❌ 只核实「技术上能不能做」，不核实「有没有对象可做」。

## 断言有效性自检

补完契约/回归断言后，**必须注入一次人为漂移**确认它真会失败，否则可能是永远为绿的假测试。

```bash
cp <产物文件> /tmp/bak
sed -i "s/  <既有字段>/  <既有字段>\n  fake_field?: string/" <产物文件>
pytest <断言测试> -q      # 必须失败，且失败信息能指出具体位置
cp /tmp/bak <产物文件>
```

判据：失败信息应精确指出**哪个对象、哪一侧、哪些字段**，而不是笼统报错。

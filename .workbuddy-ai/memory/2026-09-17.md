  ① 切前 `git status --porcelain -uall` 必须为空；
  ② 未提交改动先提交到当前分支，或 `git stash push -u -m "<说明>"` —— **`-u` 不可省**，`git stash` 默认不含未跟踪文件，而新建文件正是最容易无声丢失的一类；
  ③ 切后校验 `git status` 无成片 ` D`，抽查关键目录已跟踪文件仍在磁盘上。

## 决策与理由

用户提出 `agent_memory/` 存在轻中度冗余（同一信息可能被要求写两遍），主张 7 → 5。评审结论：**方向对，砍对了 req/bug 合并与 progress 双轨收紧，只砍错一个（changelog）**。用户采纳「5 文件方案」并落地。

### 采纳前的 5 处修正（关键，勿回退）

1. **合表 ≠ 合字段**：req / bug 字段集不同（bug 需复现步骤·环境·严重度·影响版本；req 需验收标准·DoR），合并后按 `type` 保留字段模板，不压成平表。真正冗余的是**流程**（两个台账、两套状态机、两处登记），不是信息。
2. **`type=risk` 必须带具名责任人与失效期**：风险可永不关闭，否则会被当成「没做完的需求」长挂或被当成「修好的 Bug」误关。
3. **`changelog.md` 不得用 git 提交历史代替**：git log 记「代码何时变成这样」，changelog 记「需求/决策/Bug 何时变过」；粒度与对象不同，决策可能无任何代码变更，无法从 git 反查。省掉 changelog = 7→4，代价不成比例。
4. **`progress.md` 清空前必须把关键节点（决策/上线/复盘结论）写入 changelog**：原规则只说「任务完成即清空」，没说清空后归口，会丢历史。
5. **必须同步改「文档同步更新矩阵」**：原矩阵把「需求记录」与「Bug 台账」列为两个必须更新项，合并后不改即规则自相矛盾。

### 核心洞察

用户那句「每个信息只能有一个主文件」**不是新原则**，它就是既有的「单一维护源」铁律在记忆目录的落地。因此**没有新增原则**，只做落地——避免规则自身双源。

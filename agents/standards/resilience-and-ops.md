# 高可用与运维规范

## 目的

让系统在**依赖故障、流量突增、发布失误、机房级事故**四类冲击下仍可服务，或在承诺的 RTO / RPO 内恢复（取值见 `agents/standards/nfr-baseline.md` §一、§三），且每次故障都能转化为可验证的改进。

## 适用范围

所有被部署运行、对外提供服务或承载数据的产出物。S/A 级强制全部章节；B 级强制 §二、§四、§五、§六、§七；C 级强制 §二（幂等与超时）、§五（可回滚）、§六（日志与最小告警）。

## 约束等级

见 `README.md` 词表。数值指标引自 `nfr-baseline.md`，本文件只定义**参数选取规则**与**执行要求**，不重复数值。

---

## 一、冗余与故障域隔离

**必须**：

1. **无单点**：S/A 级任一组件（应用、数据库、缓存、MQ、网关、DNS、证书、定时任务调度）不得存在单实例单点；B 级允许单实例，但**必须**有重建方案且实测重建耗时 ≤ 该级 RTO。
2. **故障域明确**：在设计文档中标注每个组件的故障域维度——进程 / 宿主机 / 机架 / 可用区 / 地域。冗余副本**禁止**落在同一故障域（同宿主机、同可用区的「双机热备」不构成高可用）。
3. **故障转移可验证**：**必须**实测切换，记录切换耗时与切换期间的行为（是否丢请求、是否降级、客户端是否自动重连）。**未实测的故障转移视为不存在**。
4. **容量冗余**：任一故障域整体失效后，剩余容量**必须**能承载峰值负载（稳态水位约束见 `nfr-baseline.md` §4.2，即为留出该余量）。
5. **依赖降级**：对每个外部依赖声明「不可用时的行为」——本地缓存兜底 / 返回降级结果 / 排队重试 / 快速失败。**禁止**出现「依赖挂了我也挂」且无声明的情况。

## 二、容错模式与参数

### 2.1 超时

**必须**：每个跨进程调用都设超时，且**下游超时之和 < 上游超时**。默认起点见 `nfr-baseline.md` §2.3。**禁止**出现无超时的同步调用。

### 2.2 重试与退避

**必须**：重试满足全部条件，缺一即不得重试：

1. **幂等** —— 非幂等操作重试会重复扣款/重复下单，**禁止**重试（改为先查后写或引入幂等键）；
2. **有上限** —— 默认最多 3 次（含首次），可通过配置调整并说明依据；
3. **退避** —— 指数退避 + 随机抖动（jitter），避免重试风暴同步打向下游。默认序列 `100ms → 300ms → 900ms`，抖动 ±20%；
4. **区分错误类型** —— 仅对**可重试错误**重试（超时、连接失败、429、5xx）；对 4xx 参数错误、业务失败**禁止**重试；
5. **有熔断保护** —— 重试必须受熔断器约束，否则重试会放大故障。

### 2.3 熔断

**必须**：调用外部依赖（跨服务、第三方 API、数据库代理）时配置熔断器：

- 触发条件：滑动窗口内失败率 ≥ 50% 且请求数 ≥ 20（窗口 10 s）；
- 半开探测：熔断后 30 s 进入半开，放行少量探测请求；
- 恢复条件：连续探测成功 ≥ 5 次则关闭；
- 熔断期间的行为**必须**显式定义（快速失败并返回可重试错误，或走降级分支），**禁止**静默返回空值/默认值而不记日志。

### 2.4 限流

**必须**：按**调用方 / 租户 / 接口**三个维度至少其一限流，并明确：

- 限流算法与阈值来源（容量压测结果的 80% 或业务配额）；
- 超限响应**必须**可识别（HTTP 429 或等价业务码）并携带重试建议（`Retry-After`）；
- 关键接口与普通接口**禁止**共用同一令牌桶（避免非关键流量挤占关键链路）。

### 2.5 降级

**必须**：为每个非核心功能定义降级策略与**触发条件**，且触发条件必须可达可验证（见 `anti-patterns.md`「静默降级」）：

| 功能类型 | 降级方式 | 必须记录 |
|---|---|---|
| 推荐/个性化 | 回退到默认内容 | 降级日志 + 降级指标 |
| 非核心统计/报表 | 暂停计算，返回缓存或提示稍后 | 暂停原因与恢复条件 |
| 写操作 | **禁止**降级为丢弃；可降级为排队（有上限）或明确拒绝 | 拒绝量指标 + 告警 |

**禁止**：降级后用户与运维都无法感知（无日志、无指标、无告警）。

### 2.6 隔离舱与背压

**必须**：

- 不同租户、不同调用方、不同业务类型的流量**禁止**共用无上限队列；关键与非关键流量**必须**资源隔离（独立线程池/连接池/队列）；
- 队列**必须**有容量上限与明确的满队列行为（拒绝并返回可重试错误 / 阻塞等待 / 丢弃低优先级），**禁止**静默丢弃；
- 过载时**必须**有背压机制（拒绝新请求优于堆积到内存溢出）。

### 2.7 幂等

**必须**：所有写接口幂等（要求见 `nfr-baseline.md` §五）。幂等实现**必须**处理并发同键请求（唯一约束或分布式锁），不能只靠「先查再写」——并发下仍会重复。

## 三、容量规划与压测

**必须**：容量模型与压测要求见 `nfr-baseline.md` §四。本节补充执行层面的强制项：

1. **压测环境**：压测环境与生产环境的差异（实例规格、数据量、依赖 Mock、网络延迟）**必须**列表说明；差异导致结论不可信时**必须**标注为「待实机回归」。
2. **数据规模**：压测数据量**必须**接近生产量级（同一数量级）；用空库压测得出的结论**禁止**作为容量依据。
3. **全链路压测**（S 级必须）：覆盖网关 → 应用 → 缓存 → 数据库 → 下游依赖的完整链路，并明确压测流量与生产流量的隔离方式（影子表/影子库/流量标记）。
4. **热点识别**：压测报告**必须**包含热点分析（最慢接口、最热 key、最集中分片、锁等待）。
5. **破坏性压测**（S 级必须）：加压至出现拐点，记录容量上限、首个饱和资源、系统在过载下的行为（是否优雅拒绝还是雪崩）。
6. **稳定性测试**：S/A 级**必须**做持续负载测试，时长 ≥ **8 小时**（S 级 ≥ 24 小时），通过标准为无内存泄漏（RSS 增长 ≤ 5%）、无连接泄漏、延迟分位不随时间恶化。

## 四、部署拓扑与弹性伸缩

**必须**：

- 部署拓扑图（含网络分区、依赖、数据流向）写入设计文档；
- 环境一致性：开发/测试/生产使用同一构建产物，差异只在配置；**禁止**手工在生产改代码或配置后不同步回仓库（配置漂移视为缺陷）；
- 变更可追溯：每次部署记录 commit hash、镜像/制品版本、配置版本、执行人、时间；
- 弹性伸缩：伸缩指标、阈值、冷却时间、最小/最大实例数明确（要求见 `system-design.md` §六）；
- 定时任务与批处理**必须**具备多实例下的互斥机制（分布式锁/leader 选举），**禁止**依赖「只有一个实例」的隐含假设。

## 五、容灾、备份与恢复

**必须**：

- 备份频率、RTO/RPO 目标、演练周期见 `nfr-baseline.md` §三；
- 备份**必须**加密，访问权限最小化，介质与生产**不同故障域**；
- 恢复步骤**必须**是脚本化或可复制的清单（**禁止**「凭经验恢复」），且**必须**实际演练过一次；
- 演练记录**必须**包含：演练时间、实测 RTO/RPO、失败环节、修复动作、责任人、下次演练时间；
- 恢复验证**必须**验证数据完整性（行数/校验和/关键业务一致性），不只是「服务起来了」。

---

## 六、发布策略与回滚

**必须**：发布策略在发布前明确选择，并写入发布说明：

| 策略 | 适用 | 必须配套 |
|---|---|---|
| 灰度（按用户/流量比例） | 绝大多数变更 | 灰度比例与推进节奏、观察指标、暂停条件 |
| 蓝绿 | 需要秒级切换 | 双环境资源、数据兼容（双向兼容或单向不可逆时禁止蓝绿） |
| 金丝雀 | S/A 级高风险变更 | 金丝雀实例隔离、流量比例 ≤ 5% 起、自动回滚触发条件 |

**必须**：

1. **回滚预案**：每次发布前提供回滚方案，含回滚命令、预计耗时、回滚后数据一致性处理方式。**无回滚方案的发布不得执行**（见 `anti-patterns.md`「无回滚」）。
2. **回滚判据量化**：明确「什么指标到什么程度就回滚」（如「5 分钟内错误率 > 1%」或「P99 > 1 s 持续 3 分钟」），不依赖人工感觉。
3. **前向兼容**：灰度期间新旧版本**必须**能共存（数据库 schema、消息格式、接口契约同时兼容两个版本）。**禁止**依赖「一次性全量切换」的不可逆变更。
4. **可回滚性验证**：S 级变更**必须**在测试环境实际执行一次回滚；A 级**应该**执行。
5. **发布窗口与冻结期**：S/A 级**禁止**在业务高峰与重大活动期间发布；错误预算耗尽期间**必须**冻结功能发布（见 `nfr-baseline.md` §2.4）。

## 七、监控、告警与应急

**必须**：

- 观测字段与告警要求见 `nfr-baseline.md` §六；
- **仪表盘**：S/A 级**必须**有全局仪表盘，至少含 SLO 达成率、错误预算余额、延迟分位、错误率、饱和度、核心业务指标；仪表盘链接写入项目 README 或计划文档；
- **值班与升级**：S/A 级**必须**明确值班责任人与升级路径（一级响应时限、升级触发条件、二线/三线联系人）；**禁止**「告警发了没人管」；
- **Runbook**：每类告警**必须**对应一份 Runbook，含现象、判定、处置步骤、验证恢复的方法、止损动作（先止损后定位）；
- **审计**：敏感操作留审计日志（见 `nfr-baseline.md` §七）。

## 八、混沌工程与演练

**必须**（按级）：

| 演练类型 | S | A | B | C |
|---|---|---|---|---|
| 依赖故障注入（下游超时/报错） | 每季度 | 每半年 | 可以不 | 可以不 |
| 实例/节点故障（杀进程、下线实例） | 每季度 | 每半年 | 每年 | 可以不 |
| 全链路容灾切换 | 每季度 | 每半年 | 每年 | 交付前一次恢复验证 |
| 容量突增（按 `nfr-baseline.md` §4.3 的破坏性压测倍数加压） | 每季度 | 每半年 | 可以不 | 可以不 |

**必须**：每次演练前定义**假设**（如「杀掉一个实例，P99 上升不超过 20%，无请求失败」）与**止损条件**；演练后产出报告，含假设是否成立、暴露的缺陷、修复责任人与期限。**禁止**演练不设假设、不设止损、不留记录。

## 九、故障复盘与持续改进

**必须**：

- S/A 级故障（可用性下降、数据错误、资损、安全事件）**必须**在 **3 个工作日**内完成复盘，产出文档落盘 `.agent_docs/incidents/YYYY-MM-DD-<slug>.md`；
- 复盘内容**必须**包含：时间线（含时区）、影响面（受影响用户/请求量/金额）、根因（技术根因 + 流程根因）、**为什么监控没提前发现**、处置过程、改进项（每项具名责任人与截止时间）；
- **禁止**把复盘写成「人为疏忽」结论 —— 必须落到系统或流程改进上（人的失误是系统缺少防错的证据）；
- 改进项**必须**在下一阶段门禁中回填完成状态；未完成的改进项**必须**有新的失效期与责任人，**禁止**「后续优化」式表述；
- 同类故障重复出现时，**必须**把对应约束固化为本目录或 `AGENTS.md` 的强制项，并补一条结构性测试或告警。

## 验收标准

- [ ] 无单点，故障域标注明确，冗余副本跨故障域
- [ ] 故障转移实测过，有切换耗时与行为记录
- [ ] 所有跨进程调用有超时，且下游超时之和 < 上游超时
- [ ] 重试满足幂等 + 上限 + 退避 + 错误类型区分 + 受熔断约束
- [ ] 熔断/限流/降级参数已配置，触发条件可达，降级有日志与指标
- [ ] 队列有上限，背压行为明确，无静默丢弃；关键流量资源隔离
- [ ] 按级完成压测与稳定性测试，报告含热点与瓶颈
- [ ] 部署拓扑图与环境一致性机制已建立，定时任务有互斥
- [ ] 备份已实测恢复并验证数据完整性，RTO/RPO 实测值有记录
- [ ] 发布有灰度/蓝绿/金丝雀策略 + 量化回滚判据，回滚已验证
- [ ] 仪表盘、值班升级路径、Runbook 齐备
- [ ] 按级完成演练，含假设与止损；故障复盘在 3 个工作日内完成

## 反例

| 反例 | 违反项 | 正确做法 |
|---|---|---|
| 「同机房两台机器，算高可用」 | §一 故障域 | 跨可用区/机架，标注故障域维度 |
| 「调用了外部 API，没设超时」 | §2.1 | 设超时并保证下游 < 上游 |
| 「失败就重试 10 次」 | §2.2 | 幂等 + 上限 3 次 + 指数退避 + 抖动 |
| 「队列满了就丢，反正会重发」 | §2.6 | 明确背压行为，禁止静默丢弃 |
| 「先上线，出问题手动回滚」 | §六 | 回滚预案 + 量化判据 + 已演练 |
| 「告警发到群里，谁看到谁处理」 | §七 | 值班责任 + 升级路径 + Runbook |
| 「这次是人疏忽，下次注意」 | §九 | 落到系统防错改进，具名责任人与期限 |
| 「压测在空库上跑，QPS 很高」 | §三 | 数据量接近生产量级，否则结论不可用 |

## 检查清单

- [ ] 单点排查完成（应用/DB/缓存/MQ/网关/DNS/证书/调度）
- [ ] 故障转移与容灾演练已实测并留记录
- [ ] 容错五件套（超时/重试/熔断/限流/降级）参数齐备且触发条件可达
- [ ] 幂等、背压、隔离舱已落地
- [ ] 压测/稳定性测试按级完成，差异与待实机项已标注
- [ ] 发布策略、回滚预案、回滚判据、冻结期规则已明确
- [ ] 仪表盘 + 值班升级 + Runbook 已建立
- [ ] 演练按级执行，故障复盘 3 个工作日内完成，改进项有责任人与期限

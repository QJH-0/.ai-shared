# 生命周期验收与门禁

## 任务适用规则

先判断本次任务风险，再确定需要的流程。`SERVICE_TIER` 表示服务故障影响，不表示每次变更都要重做完整生命周期。

| 任务 | 适用流程与记录 |
|---|---|
| 咨询、只读定位或调用链分析 | 回答问题并附证据；作为后续决策输入的复杂研究落盘，不强制容量或竞品分析 |
| 目标明确、局部、可逆且不涉及安全/数据/契约/部署的小改动 | 查上下文、最小修改、相关验证；可对话交付，不重复设计审批，不强制独立计划与运维报告 |
| 跨模块、高风险或关键决策未明确的变更 | 相关调研、方案与影响分析、必要确认、实施、独立测试与审查；按涉及章节留证 |
| 生产发布 | 在提交门禁放行后，由 sre 独立核验生产就绪与上线门禁 |

- 涉及持久化结构的变更仍须遵循 AGENTS.md 的用户确认关卡；文件删除、Git 和生产写操作仍须遵循授权规则。
- 调研、方案和验证只覆盖任务与影响路径，不因“高等级服务”扩大无关改动或验收。
- 已有系统沿用有效定级与基线；新系统或影响等级变化时由 analyst 定级。不得为了绕过要求降低等级。
- 确有生产影响的部署、数据、容量变更提前评审相关运维风险；不发布时不要求签署上线门禁。
- 正式提交需要 tester 与 reviewer 的独立门禁；轻量开发自验证不替代该门禁，也不授权提交。

## 门禁状态与报告

本节是严重程度、`GATE_STATUS`、`RELEASE_GATE`、合并、豁免和报告协议的唯一维护源；角色与其他标准只引用。

### 严重程度与置信度

问题类别（正确性、安全、性能等）与严重程度分开记录，不能按类别直接定级。

| 严重程度 | 影响与处置 |
|---|---|
| P0 | 紧急、广泛的资损、数据破坏、安全失守或核心服务不可用；已确认即阻断 |
| P1 | 必须在本次交付前修复的功能、安全、兼容或可靠性缺陷；已确认即阻断 |
| P2 | 非阻断的局部问题或优化建议，说明影响 |
| P3 | 低影响的可选改进 |

置信度使用 CONFIRMED（证据已确认）、PLAUSIBLE（可能，待验证）、UNCERTAIN（证据不足）。疑似 P0/P1 不当作已确认缺陷，但未消除的关键风险不得计为通过。反模式颜色只提示风险，不替代按实际影响、服务等级和证据定级。

### 提交门禁 GATE_STATUS

Tester 与 reviewer 分别填写本角色结果，按以下规则生成其状态；实施者不得代签。

| 状态 | 条件 |
|---|---|
| `FAILED` | 已确认 P0/P1、相关关键行为新回归、适用的强制验收明确失败 |
| `PENDING` | 尚未完成、当前变更证据失效、相关关键路径未验证或疑似 P0/P1 未消除 |
| `PASSED_WITH_WARNINGS` | 本次强制验证已满足，仅有不影响本次关键路径的已知失败、非关键限制或需跟踪事项，并附影响证据 |
| `PASSED` | 本次适用要求满足，无阻断、待核验关键风险或需跟踪警告；P2/P3 建议可单独记录 |

合并顺序：任一角色 FAILED → FAILED；否则任一缺失或 PENDING → PENDING；否则任一 PASSED_WITH_WARNINGS → PASSED_WITH_WARNINGS；否则双方 PASSED → PASSED。

仅 PASSED、PASSED_WITH_WARNINGS 放行提交。警告须说明影响与处置；已获授权且无新增关键决策时不重复询问。门禁放行仍不构成 commit、push、merge 授权。

### 上线门禁 RELEASE_GATE

上线门禁由 sre 独立判定，不由提交门禁自动生成。

| 状态 | 条件 |
|---|---|
| `NOT_READY` | 初始状态；提交门禁未放行、关键证据未验证、适用强制项失败且无有效豁免、或不可豁免缺陷存在 |
| `READY_BY_EXCEPTION` | 提交门禁已放行，其余适用项满足；可豁免差距经用户书面批准并具备四要素 |
| `READY` | 提交门禁已放行，全部适用强制项满足，证据有效，无未处理阻断或豁免 |

四要素：书面理由、具名责任人、失效日期或触发条件、补偿措施；豁免写入运维报告并由门禁报告链接。非适用项是范围判断，不是豁免，须说明依据。

不可豁免：已确认 P0/P1、凭据泄露或鉴权缺陷、关键路径回归或未验证、无可执行回滚的生产发布，以及 S/A 级相关的冗余、容灾、容量和观测强制项未满足。不得以“后续优化”代替验收；非关键差距只有按上述规则批准后才可例外上线。

### 报告协议与证据有效性

- 报告路径：`.agent_test/gate/report.md`。详细测试、审查和运维报告各有唯一来源，门禁只存状态、摘要与指针。
- Tester 只更新测试部分，reviewer 只更新审查部分，sre 只更新上线部分；更新前读取现有内容，共享报告串行修改并保留他人部分。
- 首次创建时测试与审查未完成部分为 PENDING、上线为 NOT_READY；更新测试/审查后重算 GATE_STATUS。
- 记录被验证的基准 commit、变更文件内容摘要/哈希（含未跟踪文件），发布时记录制品及配置版本；只有 HEAD 不足以证明未提交内容已验证。
- 证据须包含范围、环境、时间、执行命令、退出码及日志/截图等路径。被验证内容变化后，受影响角色结果回到 PENDING，上线回到 NOT_READY；重新验证或有证据证明不受影响后才可恢复。
- 不相关变更与未变化的生产基线可引用仍有效证据，说明适用依据；禁止把旧报告直接用于未验证的新行为。
- 报告按下列结构填写实际值，不保留占位符；发布前检查初始状态与证据有效性。

```markdown
# Gate Report
GATE_STATUS=PENDING
RELEASE_GATE=NOT_READY

## 被验证变更
基准 commit、文件内容摘要/哈希、环境、时间；发布时另记制品/配置版本。

## 测试结果
状态、判定人、通过/失败/跳过统计、失败分类、原始证据、详细报告路径。

## 审查结果
状态、判定人、P0–P3 与置信度摘要、覆盖范围、原始证据、详细报告路径。

## 上线结果
判定人、适用范围、未验证或豁免项、运维报告路径。
```

## 一、阶段总览

仅启用任务所需阶段，阶段验收不替代操作授权。

| 阶段 | 主责 | 交付 |
|---|---|---|
| 调研 | researcher | 回答研究问题，结论有证据；复杂决策研究写 `.agent_docs/research/` |
| 需求分析 | analyst | 目标、方案、相关影响与验收；复杂方案写 `.agent_docs/plans/` |
| 开发 | coder | 范围内实现、相关验证与自审；复杂实现写 `.agent_docs/impl/` 或计划执行记录 |
| 测试与审查 | tester / reviewer | 独立验证与审查；正式报告写 `.agent_docs/tests/`、`.agent_docs/reviews/`，合并提交门禁 |
| 系统设计与运维 | sre | 相关风险评审；发布前核验并写 `.agent_docs/ops/` 与上线门禁 |

## 二、调研验收

- 输入：研究问题、边界与可访问来源明确。
- 输出：直接回答问题，代码库发现附 file:line，外部事实附一手来源与获取时间；未确认项标 `[待验证]` 并给验证方法。
- 新系统、架构或选型研究按影响补充用户场景、规模增长、容量假设、安全/成本约束、技术风险及相关非功能需求；有真实选择时比较替代方案。
- 规模与容量数字注明实测、业务目标或假设及推导；单点定位不强制这些内容。
- 复杂研究落盘，简单查询可仅对话返回；不得以调研报告存在代替结论有证据。

## 三、需求分析验收

- 输入：用户目标、已有实现和关键约束可查证；未确认的关键决策已列明。
- 方案包括目标/范围、现状证据、推荐方案与理由、任务/验收、风险与回滚；只写相关维度。
- 新系统或等级变化时定 SERVICE_TIER，按 nfr-baseline 选相关目标，记录业务假设与验证方式；已有系统引用有效基线。
- 涉及运行行为时覆盖相关异常与边界：依赖故障、超时、并发/重复提交、空值/超限、权限；不适用项不强制凑齐。
- 架构或技术存在实质取舍时比较可行方案；涉及持久化结构按 AGENTS.md 第三节输出方案并获确认。
- 已获授权的小改动不重复审批；重大变更和关键用户决策确认后才推进相关实施。复杂方案落盘并保留确认出处。

## 四、开发验收

先读目标及依赖，核对范围、验收和授权。按变更影响读取相关规则，避免重复清单：

| 影响 | 要求来源 |
|---|---|
| 架构、接口、扩展、事务与数据演进 | `system-design.md` 相关章节 |
| 服务目标、容量、幂等、安全与数据生命周期 | `nfr-baseline.md` 相关章节 |
| 超时、重试、背压、部署与回滚 | `resilience-and-ops.md` 相关章节 |
| 静默失败等风险模式 | `anti-patterns.md` 相关条目 |
| 范围、代码质量、注释、文件与授权 | AGENTS.md；语言注释细则见 coder.md |

完成条件：范围内实现与自审完成，相关验证有原始证据，无已确认阻断问题。行为变更须沿用户路径验证；UI 截图核对；文档/配置无行为变化时做适用的内容与结构检查，不为形式新增测试。复杂实现记录落盘，轻量任务可对话交付。

## 五、测试验收

输入：被测内容和环境明确；按本次变化制定用例。下表用于新系统、相关能力新增或受影响路径；已有系统引用基线，不要求每次重跑无关层次或全量套件。

### 分层测试策略（按级强制）

| 层次 | 覆盖要求 | S | A | B | C |
|---|---|---|---|---|---|
| 单元测试 | 核心业务规则、边界、异常路径 | 必须 | 必须 | 必须 | 底线（关键路径） |
| 集成测试 | 模块交互、DB、MQ、外部依赖（可 Mock） | 必须 | 必须 | 必须 | 可以不 |
| 契约测试 | 对外接口契约与调用方兼容性 | 必须 | 必须 | 应该 | 可以不 |
| E2E | 用户关键路径（含 Web 界面浏览器自动化） | 必须 | 必须 | 应该 | 可以不 |
| 性能压测 | 见 `nfr-baseline.md` §4.3 的倍数要求 | 必须 | 必须 | 必须 | 可以不 |
| 稳定性测试 | 持续负载时长、无泄漏与分位漂移判据见 `resilience-and-ops.md` §三 | 必须 | 必须 | 可以不 | 可以不 |
| 故障注入 / 混沌 | 见 `resilience-and-ops.md` §八 | 必须 | 必须 | 可以不 | 可以不 |
| 安全测试 | 认证绕过、越权、注入、敏感数据暴露 | 必须 | 必须 | 应该 | 底线（凭据与鉴权） |
| 数据测试 | 数据完整性、迁移正确性、一致性校验 | 必须（涉及数据变更时） | 必须 | 应该 | 可以不 |

### 覆盖率门槛

| 级别 | 行覆盖率 | 分支覆盖率 | 说明 |
|---|---|---|---|
| S | ≥ 85% | ≥ 75% | 核心领域逻辑**必须** ≥ 90% 行覆盖 |
| A | ≥ 80% | ≥ 70% | 核心领域逻辑**必须** ≥ 85% 行覆盖 |
| B | ≥ 70% | ≥ 60% | — |
| C | 无门槛 | 无门槛 | 关键路径须有测试 |

**禁止**：为凑覆盖率写无断言测试；用 `--coverage` 排除规则把难测代码移出统计。覆盖率不达标时**必须**记录差距清单与补齐计划（含责任人与时间点），**禁止**「后续优化」。

覆盖率门槛用于新系统或受影响的业务模块；文档、文案与无行为变化的低风险配置不适用。关键路径失败或未验证不能用覆盖率数字掩盖，登记差距也不自动放行。

完成条件：适用测试已执行，命令、退出码与统计可追溯；失败区分回归、已知失败和环境阻塞，UI 有截图，迁移有数据及回滚验证。受限项说明具体复验路径，测试状态与门禁合并按本文件定义；关键环境不可用保持 PENDING。

## 六、生产就绪验收

## 七、证据与持续改进

- 指标按 README 的归属表引用，项目实际目标与配置记在项目文档；不在角色中重定义默认值。
- 静态检查不能替代行为验证；未执行、失败和未覆盖内容如实记录。
- 未放行不得提交或上线；两道门禁独立，授权独立。
- 复盘、覆盖率与存量差距只在相关任务或下一次受影响门禁中回填，未完成项说明责任与期限；不为补齐基线重写无关存量代码。

# 全生命周期质量门禁矩阵

## 目的

让每个阶段都有**明确的入口条件、出口条件、强制产出与证据要求**，使「未完成」无法伪装成「已完成」，使 `GATE_STATUS` 与 `RELEASE_GATE` 的判定有据可查。

## 适用范围

所有阶段的所有产出物。按 `SERVICE_TIER`（`nfr-baseline.md` §一）分级适用：S/A 级全部强制；B 级强制标 `必须` 项；C 级强制标 `底线` 项。

## 约束等级与枚举

- 约束等级词表见 `README.md`。
- `GATE_STATUS`（提交门禁）与 `RELEASE_GATE`（上线门禁）的取值定义，唯一维护源为 `AGENTS.md`「门禁状态定义」，本文件只使用、不重复定义。

---

## 一、阶段总览

| 阶段 | 主责角色 | 入口门禁（DoR） | 出口门禁（DoD） | 强制产出 |
|---|---|---|---|---|
| 1 调研 | researcher | 研究问题与边界明确 | 调研报告含规模/并发/约束/替代方案，结论有 file:line 或来源证据 | `.agent_docs/research/YYYY-MM-DD-<slug>.md` |
| 2 需求分析 | analyst | 调研结论可用或已明确标注假设 | 计划文档含 `SERVICE_TIER`、非功能需求、异常流、验收标准 | `.agent_docs/plans/YYYY-MM-DD-<slug>.md` |
| 3 开发 | coder | 计划已确认（大改动）或改动分级判定完成 | 测试通过 + 构建通过 + 自审通过 + 执行记录落盘 | `.agent_docs/impl/` 或计划文档「执行记录」章节 |
| 4 测试 | tester | 被测对象与 commit 明确，环境可用 | 分层测试执行完毕、失败已分析、报告与证据落盘 | `.agent_docs/tests/YYYY-MM-DD-<slug>.md` + `.agent_test/gate/report.md` |
| 5 系统设计与运维 | sre | 交付物已通过阶段 4，或变更涉及部署/数据/容量 | 生产就绪清单逐项回填，演练与回滚验证完成 | `.agent_docs/ops/YYYY-MM-DD-<slug>.md` + `RELEASE_GATE` 判定 |

**必须**：阶段 5 不得因为「本次只是小改动」被整体跳过——按 `AGENTS.md`「改动分级」判定为小改动时，可仅回填「生产就绪清单」中的相关项，但**必须**显式说明跳过的依据。

## 二、阶段 1 — 调研

### 入口门禁（DoR）

- [ ] 研究问题一句话可表述，边界（查什么、不查什么）明确
- [ ] 已知约束（时间、环境、可访问范围）已声明

### 强制调研项（缺一即 DoD 未达成）

| 项 | 要求 | 等级 |
|---|---|---|
| 用户与场景 | 谁用、什么场景、频次、失败时的业务影响 | 必须 |
| 业务规模与增长预期 | 当前量级 + 未来 12 个月预测 + 依据（业务目标/历史增速） | 必须 |
| 并发与容量假设 | 峰值系数、峰值 QPS/TPS、数据量级与增长速度 | 必须 |
| 合规、安全、成本约束 | 数据敏感级别、合规要求、预算与资源上限 | 必须 |
| 技术选型与风险 | 候选方案的成熟度、社区活跃度、团队熟悉度、锁定风险 | 必须 |
| 非功能需求清单 | 逐项对应 `nfr-baseline.md`，初判 `SERVICE_TIER` | 必须 |
| 竞品或替代方案对比 | ≥ 2 个可行替代方案，含「自研 vs 复用 vs 采购」维度 | 应该 |

### 出口门禁（DoD）

- [ ] 每条结论有可验证证据：代码库发现附 `file:line`；外部信息附来源与获取时间
- [ ] 未确认内容标记 `[待验证]`，未混入结论
- [ ] 报告已落盘，对话只返回浓缩结论 + 路径

### 证据要求

调研报告 + 关键发现的一手来源链接或命令输出。**禁止**用二手转述作为技术选型依据。

## 三、阶段 2 — 需求分析

### 入口门禁（DoR，未达成不得进入开发）

- [ ] 调研结论可用，或未调研的部分已明确标注为假设并列出验证方式
- [ ] `SERVICE_TIER` 已定级（取自 `nfr-baseline.md` §一）
- [ ] **功能需求**已列全：每条含输入、输出、业务规则、失败行为
- [ ] **非功能需求**已列全：可用性（SLO）、延迟目标、容量与峰值、扩展性预期、可观测性要求、安全要求、数据生命周期、依赖与降级要求
- [ ] **用户故事 + 验收标准**：验收标准可执行、可观测（不是「体验流畅」这类主观描述）
- [ ] **异常流与边界条件**：列出至少「依赖不可用、超时、并发冲突、重复提交、数据为空/超限、权限不足」六类场景的处理方式
- [ ] **依赖清单**：上下游服务、第三方、数据源，每个附「不可用时的行为」
- [ ] **不做的事**（范围边界）已显式声明
- [ ] **Definition of Ready 全部勾选**（见本节清单末尾）

### 出口门禁（DoD）

- [ ] 计划文档落盘，含「需求理解 / 非功能需求与分级 / 现状分析 / 推荐方案 / 任务拆解 / 风险与缓解 / 下一步行动」七节
- [ ] 方案对比 ≥ 2 个，含取舍逻辑与 YAGNI 裁剪说明
- [ ] 风险评估含技术、依赖、安全、容量四类，每项有缓解措施
- [ ] **回滚方案**：方案无法落地时如何安全回退
- [ ] 涉及数据/架构/接口变化时，按 `AGENTS.md`「数据变更与 DDL 确认关卡」与「跨模块变更判定」输出书面方案
- [ ] 已按 `anti-patterns.md` 自查，命中项写入「风险与缓解」

### 证据要求

计划文档 + `SERVICE_TIER` 定级依据 + 容量模型推导链（S/A 级）+ 用户对方案的确认记录。

### Definition of Ready 汇总（阶段 2 收口时逐项勾选）

- [ ] 功能需求完整且无 TBD
- [ ] 非功能需求完整且定量（引用 `nfr-baseline.md` 取值）
- [ ] 验收标准可执行可观测
- [ ] 异常流与边界条件已覆盖
- [ ] 依赖与降级行为已声明
- [ ] 范围边界（不做什么）已声明
- [ ] `SERVICE_TIER` 已定级
- [ ] 回滚方案已给出
- [ ] 方案已经用户确认

## 四、阶段 3 — 开发

### 入口门禁（DoR）

- [ ] 大改动：计划已确认；小改动：改动分级判定完成并说明依据
- [ ] 目标文件与依赖已完整阅读

### 强制开发要求

| 项 | 要求 | 等级 |
|---|---|---|
| 架构原则与边界 | 遵守 `system-design.md` §一：依赖单向、边界显式、无循环依赖、无跨层直连 | 必须 |
| API 契约与版本 | 遵守 `system-design.md` §二：契约机器可读、版本载体明确、兼容性判定记录 | 必须 |
| 错误处理 | 错误分类明确（可重试/不可重试/业务失败）；**禁止**静默失败三模式（`anti-patterns.md` 补充项） | 必须 |
| 幂等 | 所有写接口幂等，幂等键来源与去重窗口明确（`nfr-baseline.md` §五） | 必须 |
| 并发 | 池化参数有上限、背压行为明确、共享状态有并发保护、无竞态 | 必须 |
| 事务 | 事务边界明确（用例层）；跨服务一致性方案明确（避免无补偿的跨库事务） | 必须 |
| 超时与重试 | 所有跨进程调用有超时，下游之和 < 上游；重试满足五条件（`resilience-and-ops.md` §2.2） | 必须 |
| 缓存 | 三防（穿透/击穿/雪崩）已处理，失效策略明确 | 必须（用到缓存时） |
| 异步与消息 | 投递语义、消费幂等、死信处理、积压告警已定义 | 必须（用到 MQ 时） |
| 配置 | 配置集中在配置层，有默认值与缺失行为；凭据不落代码 | 必须 |
| 可观测性 | 按 `nfr-baseline.md` §六 埋入日志字段与指标；新增接口**必须**带 trace 上下文 | 必须 |
| 安全 | 认证从可信载体派生、授权服务端校验、输入白名单校验、无注入 | 必须 |
| 扩展点 | 存在变化预期的维度已留扩展点，核心流程无类型分支 | 必须 |
| 注释与代码质量 | 遵守 `AGENTS.md`「编码与注释规范」与「代码输出自检」 | 必须 |

### 出口门禁（DoD）

- [ ] 测试通过（单元 + 相关集成），构建/编译通过，类型检查通过
- [ ] 自审通过（幻觉 API、安全漏洞、逻辑错误）
- [ ] 注释与堆砌自检通过（无复述式冗余注释、无过期注释、无注释封存的废弃代码、无过程信息注释；无新旧并排 / 包装规避 / 重复防御 / 预留抽象）
- [ ] 执行记录落盘，含验证命令与实际输出摘要
- [ ] 无 `anti-patterns.md` 命中的 P0 项（🔴）
- [ ] 涉及运行行为的改动已在真实环境跑通用户路径（**禁止**用静态检查替代行为验证）

### 证据要求

执行记录 + 测试命令与实际输出（退出码）+ 构建输出 + 契约变更的兼容性判定。

## 五、阶段 4 — 测试

### 入口门禁（DoR）

- [ ] 被测对象明确（文件/模块/commit hash）
- [ ] 测试环境可用，或环境不可用已记录为阻塞（**禁止**跳过直接判定）
- [ ] 测试策略与用例清单已写入测试报告文档

### 分层测试策略（按级强制）

| 层次 | 覆盖要求 | S | A | B | C |
|---|---|---|---|---|---|
| 单元测试 | 核心业务规则、边界、异常路径 | 必须 | 必须 | 必须 | 底线（关键路径） |
| 集成测试 | 模块交互、DB、MQ、外部依赖（可 Mock） | 必须 | 必须 | 必须 | 可以不 |
| 契约测试 | 对外接口契约与调用方兼容性 | 必须 | 必须 | 应该 | 可以不 |
| E2E | 用户关键路径（含 Web 界面浏览器自动化） | 必须 | 必须 | 应该 | 可以不 |
| 性能压测 | 见 `nfr-baseline.md` §4.3 的倍数要求 | 必须 | 必须 | 必须 | 可以不 |
| 稳定性测试 | 持续负载时长、无泄漏与分位漂移判据见 `resilience-and-ops.md` §三 | 必须 | 必须 | 可以不 | 可以不 |
| 故障注入 / 混沌 | 见 `resilience-and-ops.md` §八 | 必须 | 必须 | 可以不 | 可以不 |
| 安全测试 | 认证绕过、越权、注入、敏感数据暴露 | 必须 | 必须 | 应该 | 底线（凭据与鉴权） |
| 数据测试 | 数据完整性、迁移正确性、一致性校验 | 必须（涉及数据变更时） | 必须 | 应该 | 可以不 |

### 覆盖率门槛

| 级别 | 行覆盖率 | 分支覆盖率 | 说明 |
|---|---|---|---|
| S | ≥ 85% | ≥ 75% | 核心领域逻辑**必须** ≥ 90% 行覆盖 |
| A | ≥ 80% | ≥ 70% | 核心领域逻辑**必须** ≥ 85% 行覆盖 |
| B | ≥ 70% | ≥ 60% | — |
| C | 无门槛 | 无门槛 | 关键路径须有测试 |

**禁止**：为凑覆盖率写无断言测试；用 `--coverage` 排除规则把难测代码移出统计。覆盖率不达标时**必须**记录差距清单与补齐计划（含责任人与时间点），**禁止**「后续优化」。

### 出口门禁（DoD）

- [ ] 按级完成全部强制测试层次，结果与统计写入测试报告
- [ ] 失败用例已根因分析，区分「回归」与「已知失败」，**未跳过的失败不得静默**
- [ ] 覆盖率达标，或差距清单已登记
- [ ] 原始证据齐备：实际执行命令、退出码、日志/截图/trace 路径
- [ ] 门禁报告已更新测试半，`GATE_STATUS` 按 `AGENTS.md` 合并规则更新
- [ ] 涉及 UI 的改动有截图核对证据
- [ ] 环境/凭据受限时，明确标注「待实机回归」的具体用户路径、受限原因与后续验证条件

### 证据要求

测试报告 + 门禁报告测试半 + 压测报告 + 覆盖率报告 + 失败证据（截图/trace/日志）。

- [ ] 部署拓扑、数据流向、依赖清单已明确

### `RELEASE_GATE` 判定（取值定义见 `AGENTS.md`）

| 判定 | 条件 |
|---|---|
| `READY` | 该级别全部「必须」项达标，证据齐备，无 P0 反模式命中 |
| `READY_BY_EXCEPTION` | 仅 C 级可对「底线」外的项豁免，或经用户书面批准；**必须**同时具备书面理由、具名责任人、失效期、补偿措施四要素 |
| `NOT_READY` | 任一「必须」项未达标，或豁免缺四要素中任一项，或命中 P0 反模式 |

**必须**：`RELEASE_GATE` 由 sre 判定并写入运维文档与门禁报告；**禁止**由实施者自判自签。

### 出口门禁（DoD）

- [ ] 生产就绪清单逐项回填，每项附证据位置（命令输出、截图、报告路径、监控链接）
- [ ] `RELEASE_GATE` 已判定并写入 `.agent_test/gate/report.md`
- [ ] 发布说明含：变更内容、影响范围、发布策略、观察指标、回滚判据、回滚步骤、执行人
- [ ] 演练与回滚验证记录已落盘
- [ ] 未验证项、待实机回归项、阻塞项已显式列出并指定责任人与失效期

### 证据要求

运维文档 + 生产就绪清单回填 + 压测报告 + 演练记录 + 回滚验证记录 + 仪表盘与 Runbook 链接 + `RELEASE_GATE` 判定。

## 七、跨阶段一致性要求

- **术语与指标**：所有数值引自 `nfr-baseline.md`；出现第二处定义即为缺陷，须立即消除。
- **门禁联动**：`GATE_STATUS`（提交）与 `RELEASE_GATE`（上线）是两道独立门禁。`GATE_STATUS=PASSED` **不等于**可以上线——上线还需阶段 5 的生产就绪判定。
- **证据不可替代**：任何检查项都必须附实际执行输出。**不得将未运行的检查描述为通过**；lint、构建、静态断言、接口存在均不能替代行为验证。
- **阻断不可绕过**：门禁未放行时不得提交、不得发布。豁免必须走 `README.md`「豁免规则」四要素。
- **改进项闭环**：故障复盘的改进项、覆盖率差距清单、存量差距清单，**必须**在下一阶段门禁中回填状态；未完成的须有新的失效期与责任人。

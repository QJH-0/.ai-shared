# 非功能需求基线（NFR Baseline）

## 目的

让「可用、并发、扩展、可观测、安全」在**调研与需求阶段就出现并定量**，而不是上线前才补。本文件是所有可度量数值的唯一维护源。

## 适用范围

任何将被部署、被外部调用、被他人依赖或承载业务数据的产出物（服务、接口、任务、批处理、前端应用、CLI 工具）。纯本地一次性脚本按 C 级处理，仍须满足「安全基线」与「可回滚」两条。

## 约束等级

见 `README.md` 词表。本文件正文中每条均标注 **必须 / 应该 / 可以**。

---

## 一、服务分级（SERVICE_TIER）

`SERVICE_TIER` 的唯一维护源即本节。**需求分析阶段必须定级**并写入计划文档；未定级不得进入开发。

| 级别 | 判定标准（满足任一即归入该级） | 可用性 SLO（月度） | 允许月停机 | RTO | RPO |
|---|---|---|---|---|---|
| **S** 关键 | 资金 / 交易 / 身份认证 / 不可逆写操作；单点故障直接造成资损、数据错误或合规违规 | **99.99%** | ≤ 4.3 分钟 | ≤ 5 分钟 | **= 0**（不允许丢数据） |
| **A** 核心 | 面向外部用户的主链路，可用性直接影响营收或活跃；被其他系统强依赖 | **99.95%** | ≤ 21.6 分钟 | ≤ 15 分钟 | ≤ 1 分钟 |
| **B** 支撑 | 内部运营 / 后台 / 报表，可短时降级或延迟处理 | **99.9%** | ≤ 43.2 分钟 | ≤ 1 小时 | ≤ 5 分钟 |
| **C** 工具 | 本地脚本、一次性任务、无外部用户，失败可重跑 | **99%** | ≤ 7.2 小时 | ≤ 24 小时 | ≤ 24 小时 |

**必须**：分级结果决定本文件其余全部指标的取值，以及 `lifecycle-gates.md` 中需要提交的证据集合。定级不得为了绕过门禁而人为调低——降级必须写明理由、责任人与失效期（见 `README.md`「豁免规则」）。

**必须**：同一系统内不同接口分级不同时，按**最高**级别接口的要求设计共享资源（数据库、连接池、缓存、线程池）。

## 二、可用性：SLI / SLO / SLA

### 2.1 三个概念的口径（不得混用）

| 概念 | 定义 | 归属 |
|---|---|---|
| **SLI** | 可测量的服务质量指标，取自真实观测数据（不是估算、不是日志抽样推断） | 工程内部 |
| **SLO** | SLI 的目标值 + 统计窗口（如「30 天滚动窗口内成功率 ≥ 99.95%」） | 工程内部承诺 |
| **SLA** | 对客户的**合同**承诺，含违约赔偿条款 | 商业/法务，**必须** ≤ 对应 SLO（留出安全余量） |

**必须**：SLA 阈值严于 SLO 时（即 SLA 数值比 SLO 更高）视为缺陷——对外承诺超出内部目标，工程侧无缓冲。

### 2.2 SLI 最小集合（按级必选）

| SLI | 计算口径 | S | A | B | C |
|---|---|---|---|---|---|
| 可用性 | `成功请求数 / 总请求数`（按分钟粒度聚合） | 必须 | 必须 | 必须 | 可以 |
| 延迟 | P50 / P95 / P99 响应时间（不含客户端网络耗时） | 必须 | 必须 | 必须 | 可以 |
| 错误率 | `5xx + 业务失败码 / 总请求数` | 必须 | 必须 | 必须 | 可以 |
| 饱和度 | CPU / 内存 / 连接池使用率 / 队列深度的峰值占比 | 必须 | 必须 | 应该 | 可以 |
| 数据新鲜度 | `当前时间 - 数据最后写入时间`（异步链路、缓存、派生数据必选） | 必须 | 必须 | 应该 | 可以 |

**必须**：成功/失败必须有明确判定规则并写入代码（哪些状态码、哪些业务码计入失败），不得由监控侧猜测。

### 2.3 延迟目标（服务端处理耗时，不含网络传输）

| 级别 | P50 | P95 | P99 | 超时上限 |
|---|---|---|---|---|
| S | ≤ 50 ms | ≤ 200 ms | ≤ 500 ms | ≤ 1 s |
| A | ≤ 100 ms | ≤ 300 ms | ≤ 800 ms | ≤ 2 s |
| B | ≤ 200 ms | ≤ 500 ms | ≤ 1.5 s | ≤ 5 s |
| C | 无硬性 | 无硬性 | 无硬性 | ≤ 30 s |

**必须**：调用链上每一跳都设置超时，且**下游超时之和 < 上游超时**（否则上游永远等不到下游返回，超时形同虚设）。默认取值：内网 RPC ≤ 1 s，HTTP 外部依赖 ≤ 3 s，数据库查询 ≤ 2 s，队列消费单批 ≤ 30 s。

**禁止**：出现「无超时」的同步调用——无限等待会把局部故障放大为全链路堆积。

### 2.4 错误预算

**必须**：S/A 级服务按 SLO 计算错误预算，并在监控面板上可视。

- 月度错误预算 = `(1 - SLO) × 月度总请求数`
- 预算消耗 ≥ 50% → **应该**暂停非必要的非功能特性上线，优先修稳定性
- 预算消耗 100% → **必须**冻结功能发布，仅允许修复型变更；恢复条件与责任人写入计划文档

## 三、容灾：RTO / RPO 与备份

| 级别 | 部署形态（必须） | 备份频率（必须） | 恢复演练（必须） |
|---|---|---|---|
| S | 同城多可用区双活 + 异地容灾；无单点 | 连续备份 / 增量 ≤ 5 分钟 | 每季度一次真实切换演练，附耗时记录 |
| A | 多实例冗余 + 故障域隔离（不同宿主机/可用区） | 增量 ≤ 1 小时，全量每日 | 每半年一次恢复演练 |
| B | 至少 2 实例；单实例时须有重建方案且实测重建耗时 ≤ 该级 RTO | 全量每日 | 每年一次恢复演练 |
| C | 单实例可接受，但配置与数据须可重建 | 交付前一次 | 交付前验证一次恢复步骤 |

**必须**：
- 备份与恢复步骤必须**实际执行过一次并记录结果**，只写文档未验证的备份视为不存在；
- 恢复演练记录须包含：演练时间、RTO 实测值、RPO 实测值、失败环节、修复动作、责任人；
- 备份介质与生产环境**不得**共用同一故障域（同机房、同账号、同存储桶视为共用）。

## 四、性能与容量

### 4.1 指标定义（口径统一，禁止混用）

| 指标 | 口径 |
|---|---|
| QPS | 每秒请求数（读 + 写合计，须标注是否含缓存命中） |
| TPS | 每秒**完成的事务**数（含提交/回滚，写操作按事务计） |
| 并发连接数 | 同时处于已建立连接状态的连接数（区别于并发请求数） |
| P95 / P99 | 分位延迟，须标注统计窗口（如 5 分钟滑动窗口） |
| 饱和度 | 资源使用率峰值 / 容量上限 |
| 峰值系数 | `峰值 QPS / 日均 QPS`，**必须**由历史数据或业务模型得出，不得拍脑袋 |

### 4.2 容量规划要求

**必须**在需求分析阶段产出容量模型，包含：

1. **峰值模型**：日活/调用方数量 → 单用户请求频次 → 峰值系数 → 峰值 QPS/TPS；
2. **增长预期**：未来 12 个月的量级预测与依据（业务目标、历史增速）；
3. **资源换算**：峰值 QPS → 实例数 / 连接池大小 / 缓存容量 / 存储与 IOPS / 带宽；
4. **水位约束**：稳态运行资源使用率 ≤ **70%**，峰值 ≤ **85%**，超过即触发扩容（留出故障转移余量）；
5. **弹性伸缩**：S/A 级**必须**支持水平扩缩容，扩容触发条件与冷却时间明确；B 级**应该**。

**必须**：容量结论附计算过程与假设，不允许只给结论数字（无法复核的容量结论视为未产出）。

### 4.3 压测要求（按级强制）

| 级别 | 压测类型 | 通过标准 |
|---|---|---|
| S | 全链路压测 + 破坏性压测 | 达到 **2× 峰值** 负载下 P99 不超 §2.3 上限、错误率 < 0.1%；出现拐点时记录容量上限 |
| A | 单接口 + 关键链路压测 | 达到 **1.5× 峰值** 负载下达标 |
| B | 单接口压测 | 达到 **1× 峰值** 负载下达标 |
| C | 可以不压测 | — |

**必须**：压测报告落盘，含压测脚本路径、数据规模、并发模型、实测 P95/P99、QPS/TPS 曲线拐点、瓶颈定位（CPU / IO / 锁 / 连接池 / 下游）。压测环境与生产环境的差异**必须**显式列出。

**禁止**：用「本地单机跑了一下没问题」代替压测结论。

### 4.4 热点与批处理

**必须**：识别热点（单 key 高频访问、单分片数据倾斜、单用户高频写）并给出处理方案：本地缓存、key 打散、分片再平衡、写合并。

**必须**：批处理任务定义单批大小、并发度、失败重试上限与退避策略，且**不得**与在线流量争抢同一资源池（须有独立线程池/队列或限流）。

## 五、并发模型与资源池

**必须**明确并写入设计文档：

1. **并发模型**：线程池 / 协程 / 事件循环 / 异步回调，以及选择理由；
2. **池化参数**：数据库连接池、HTTP 连接池、线程池的 `max`、`min`、队列容量、获取超时。**禁止**使用无上限队列（会把过载转为内存溢出与雪崩）；
3. **背压**：队列满时的行为必须明确定义（拒绝并返回可重试错误 / 阻塞等待 / 丢弃低优先级），**禁止**静默丢弃；
4. **无状态**：S/A 级服务**必须**无状态（会话、上传中间态、定时状态外置到 Redis / 对象存储 / 数据库），以支持水平扩展与任意实例重启；
5. **幂等**：所有写接口**必须**幂等。幂等键来源明确（业务单号 / 客户端请求 ID），去重窗口 ≥ 客户端重试窗口（默认 ≥ 24 小时），去重存储的故障降级行为必须显式定义（fail-closed 拒绝写 vs 放行并记录，二选一写清楚）。

## 六、可观测性最小字段集

**必须**：S/A 级服务接入日志、指标、链路追踪三件套；B 级至少日志 + 指标；C 级至少结构化日志。

### 6.1 日志（结构化，单行 JSON 或等价键值对）

每条日志**必须**包含：`timestamp`（ISO 8601 含时区）、`level`、`service`、`trace_id`、`span_id`、`message`、`error.type`、`error.message`、`duration_ms`。

**禁止**：日志中输出凭据、令牌、完整身份证/银行卡/手机号（PII 必须脱敏或哈希）；用 `print`/`console.log` 代替结构化日志；捕获异常后不记录异常类型与消息（见 `anti-patterns.md`）。

### 6.2 指标

**必须**暴露：请求量、错误数、延迟分位（P50/P95/P99）、饱和度（CPU/内存/连接池/队列）、业务指标（按业务定义，如订单创建数、支付成功率）。

**必须**：指标命名遵循 `{namespace}_{subsystem}_{metric}_{unit}`（如 `svc_order_create_duration_seconds`），并带 `service`、`env`、`instance` 标签。**禁止**把用户 ID、订单号等高基数维度作为标签。

### 6.3 链路追踪

**必须**：跨服务调用传递 `trace_id`；跨进程边界（HTTP header / MQ header / 定时任务上下文）的传递方式明确。异步与批处理链路**必须**能被追溯（至少记录上游 `trace_id`）。

### 6.4 告警

**必须**：告警基于 SLI 而非单机瞬时指标，且满足：

- 每条告警有**明确处置动作**（谁、做什么、在哪看）与升级路径；
- 阈值来自 SLO 推导（如「5 分钟错误率 > 1% 持续 2 分钟」），不是「CPU > 80%」这类无业务含义的裸指标；
- 告警**必须**可区分「真实故障」与「已知波动」，重复告警须抑制，避免告警疲劳；
- 每条告警**必须**配一个 Runbook 路径（可写在同一文档的「应急」章节）。

## 七、安全基线

| 项 | 要求 | 等级 |
|---|---|---|
| 认证 | 身份只从可信载体派生（令牌 `sub`），**禁止**从请求参数/请求体取用户身份 | 必须（S/A/B/C） |
| 授权 | 每个业务接口默认拒绝，显式放行；权限校验在服务端，**禁止**依赖前端隐藏 | 必须 |
| 最小权限 | 数据库账号、云资源、CI 令牌按最小权限授予；**禁止**共用超级账号 | 必须 |
| 凭据 | 不得出现在源码、默认值、测试、脚本、日志中（含 base64 等编码形式）；走环境变量或密钥管理服务；本地明文只落 gitignore 的 `.env` | 必须 |
| 缺失凭据行为 | fail-closed 拒绝服务并报错，或显式降级并记日志——**禁止**静默放行 | 必须 |
| 输入校验 | 所有外部输入（含 header、文件名、路径、反序列化内容）白名单校验；防注入（SQL/命令/模板/反序列化） | 必须 |
| 依赖扫描 | S/A 级每次构建执行依赖漏洞扫描；**禁止**引入有已知高危漏洞且无修复版本的依赖 | 必须（S/A） |
| 传输与存储加密 | 外部传输 TLS ≥ 1.2；S/A 级敏感数据落库加密或脱敏 | 必须（S/A） |
| 鉴权失败文案 | 不区分「用户不存在」与「口令错误」，避免账号枚举 | 必须 |
| 审计 | 敏感操作（权限变更、资金、数据导出、配置修改）留审计日志：操作者、时间、对象、前后值、来源 IP | 必须（S/A） |

**必须**：安全项不得作为「上线后补」。S/A 级服务缺失认证/授权/凭据管理任一项，直接 `RELEASE_GATE=NOT_READY`。

## 八、数据生命周期与合规

**必须**在需求分析阶段定义并写入计划文档：

1. **归属**：每类数据的 CRUD 主体（哪个服务是唯一写入方）；
2. **保留期**：每类数据的保留时长与依据（业务需要 / 合规要求）；
3. **删除规则**：软删还是硬删、级联范围、删除的不可逆性与确认机制；
4. **脱敏与最小化**：只采集业务必需字段；PII 明确标注并定义脱敏规则；
5. **导出与跨境**：数据导出场景、范围与审批；涉及跨境的**必须**标注「需确认」并交用户裁决；
6. **备份数据**同样受保留期约束（**禁止**备份成为「永久保存」的漏洞）。

## 验收标准

阶段收口时逐项核验，未达标即不得标记完成：

- [ ] `SERVICE_TIER` 已定级并写入计划文档，取值来自本文件
- [ ] 每个对外接口的 SLI 口径、SLO 目标、超时值已明确，且下游超时之和 < 上游超时
- [ ] 容量模型含峰值系数推导过程与资源换算，稳态 ≤ 70% / 峰值 ≤ 85%
- [ ] 按级完成了压测，报告落盘并含瓶颈定位与实测分位
- [ ] 写接口幂等键来源、去重窗口、降级行为已定义
- [ ] 日志/指标/追踪三件套字段齐备，告警有阈值来源、处置动作与 Runbook
- [ ] 安全基线逐项自查通过，凭据全仓 grep 确认无残留
- [ ] 数据归属、保留期、删除规则、脱敏规则已明确
- [ ] RTO/RPO 已承诺，备份与恢复步骤已实际演练并记录实测值

## 反例

| 反例 | 违反项 | 正确做法 |
|---|---|---|
| 「接口大约 200ms 吧」 | §2.3 延迟目标 | 给出 P50/P95/P99 实测值 + 统计窗口 |
| 「做了高可用，双机热备」 | §三 故障域 | 说明故障域隔离维度（机架/可用区/地域）与实测切换耗时 |
| 「日志打了，出问题能查」 | §6.1 日志字段 | 结构化日志 + trace_id 串联，缺字段等于查不到 |
| 「监控有 CPU 告警」 | §6.4 告警 | 告警基于 SLI 与 SLO 推导，附处置动作 |
| 「峰值 QPS 估 1000」 | §4.2 容量模型 | 给出日活→频次→峰值系数的推导链 |
| 「先上线，SLO 以后再定」 | 全文件 | 需求阶段定级取值，未定级不得进入开发 |

## 检查清单

- [ ] 服务已定级（S / A / B / C），未为绕门禁而人为降级
- [ ] SLO 与 SLA 关系正确（SLA ≤ SLO）
- [ ] 错误预算已计算并可视化（S/A 级）
- [ ] 备份与恢复已实测，RTO/RPO 实测值有记录
- [ ] 压测达到对应倍数峰值，报告含瓶颈定位
- [ ] 池化参数有上限，背压行为明确，无静默丢弃
- [ ] 写接口幂等，去重窗口 ≥ 客户端重试窗口
- [ ] 安全基线 10 项逐条自查，无「上线后补」项
- [ ] 数据生命周期六项已定义

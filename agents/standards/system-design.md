# 系统设计与扩展性规范

## 目的

让系统在**需求变化、流量增长、团队扩张**三种压力下都不需要推倒重来：边界清晰、契约向后兼容、扩展点预留、数据可演进。

## 适用范围

新增模块、新增服务、新增对外接口、新增持久化实体、跨模块重构，以及任何被两个以上调用方依赖的产出物。单文件且无外部依赖的改动可以不适用，但**必须**在计划文档中写明不适用的理由。

## 约束等级

见 `README.md` 词表。所有数值指标（延迟、容量、SLO）引自 `nfr-baseline.md`，本文件不重复定义。

---

## 一、架构原则与边界

**必须**遵守：

1. **依赖方向单向**：外层（接口/适配器）依赖内层（领域/用例），内层**禁止**反向依赖外层。跨层直接调用（如 Controller 直连 DAO 绕过用例层）视为缺陷。
2. **边界显式**：每个模块声明「对外暴露什么」与「内部实现是什么」，跨模块只能通过显式契约调用，**禁止**访问对方内部数据结构或私有表。
3. **单一职责到可命名**：模块/类无法用一句话命名且不出现「和」字时，说明职责不单一，**必须**拆分。
4. **分层可见**：接口层（协议适配、参数校验、鉴权）／用例层（业务编排、事务边界）／领域层（业务规则、不变量）／基础设施层（存储、外部服务、消息）四层职责**必须**在设计文档中标出。
5. **可替换基础设施**：外部依赖（数据库、MQ、缓存、第三方 API）通过接口封装，业务代码**禁止**直接 `import` 具体驱动；以便替换、Mock 与测试。
6. **无循环依赖**：模块依赖图**必须**是 DAG。发现循环依赖**必须**通过提取共享抽象或反转依赖消除，**禁止**用延迟导入、动态反射掩盖。

**应该**：DDD 战术模式（聚合、值对象、领域事件）用于业务规则复杂的领域；六边形/整洁架构用于外部依赖多、需要长期演进的系统。**禁止**为形式而套用——引入模式必须能在设计文档中说明它解决了哪个具体问题。

**禁止**：跨模块共享数据库表直接读写（见 `anti-patterns.md`「共享数据库」）。

## 二、接口契约与版本策略

### 2.1 契约

**必须**：

- 每个对外接口有**机器可读的契约定义**（OpenAPI / Protobuf / GraphQL SDL / JSON Schema 任一），与实现同源，**禁止**只在文档里手写接口说明；
- 契约包含：路径/方法、请求字段（类型、可空性、取值范围、默认值）、响应字段、错误码全集、鉴权要求、超时与重试语义、幂等语义；
- 契约变更**必须**经契约测试验证（见 `lifecycle-gates.md` 测试阶段）。

### 2.2 版本策略

**必须**明确版本载体并写入设计文档，三选一并说明理由：

| 方案 | 适用 | 版本载体 |
|---|---|---|
| URL 版本 | 对外 REST，需强隔离 | `/v1/orders` |
| Header 版本 | 内部服务，路径不变、仅 header 区分 | `X-API-Version: 2` |
| 字段级演进 | 兼容性优先的开放平台 | 只增不改，废弃走公告 |

**兼容性规则（必须）**：

| 变更类型 | 兼容性 | 处理要求 |
|---|---|---|
| 新增可选请求字段 | 向后兼容 | 可直接发布 |
| 新增响应字段 | 向后兼容 | 调用方**必须**忽略未知字段 |
| 新增枚举值 | 向后兼容（调用方须有 default 分支） | 契约中标注「可能扩展」 |
| 字段类型变更 / 语义变更 | **不兼容** | **必须**升版本 |
| 删除字段 / 改必填性 / 改默认值 | **不兼容** | **必须**升版本 |
| 收紧校验（如原允许 200 字符改为 100） | **不兼容** | **必须**升版本 |

**必须**：

- 旧版本**禁止**无预警下线：需公告期（对外 ≥ 90 天，内部 ≥ 30 天，或由用户指定并记录），并在服务端埋点统计旧版本调用量，调用量归零后方可下线；
- 接口废弃**必须**在响应中返回弃用提示（如 `Deprecation` / `Sunset` header 或等价字段），不能只发公告；
- **禁止**出现「无版本 API」——一旦发布即需版本标识（见 `anti-patterns.md`）。

**必须**：契约变更的兼容性判定结果写入交付记录，标注「已检查调用方清单」（列出全部调用方，或说明为何无法穷举）。

## 三、扩展点

**必须**：在设计阶段判定本模块是否存在「预期会变」的维度，存在则**必须**预留扩展点，并写入设计文档：

| 扩展维度 | 预留方式 | 强制场景 |
|---|---|---|
| 新增业务类型 / 渠道 | 策略注册表 + 配置化映射 | 存在 ≥ 2 个同类实现，或已知未来会新增 |
| 新增外部供应商 | 适配器接口 + SPI | 存在可替换供应商 |
| 规则/阈值/开关 | 配置中心，支持热更新与灰度 | 需要不改代码调整 |
| 流程步骤差异 | 管道/责任链，步骤可插拔 | 多租户或客户定制流程 |

**必须**：

- 扩展点通过接口 + 注册机制暴露，**禁止**在核心流程里写 `if (type == "A") ... else if (type == "B")` 式的类型分支（新增类型必须能只加文件、不改核心）；
- 配置项**必须**有：名称、类型、默认值、取值范围、生效方式（热更新/需重启）、缺失时的行为。**禁止**出现无默认值且缺失即崩的配置；
- 配置读取**必须**集中在配置层，**禁止**在业务代码中散落读环境变量（见 `anti-patterns.md`「硬编码」）。

## 四、高并发设计手段

按需选用，但**必须**在设计文档中说明「用了哪些、为什么、放弃了哪些及其代价」。

| 手段 | 要求 | 禁止做法 |
|---|---|---|
| 无状态水平扩展 | S/A 级**必须**无状态；会话、上传中间态、任务状态外置 | 用本地内存存会话或任务状态 |
| 缓存分层 | 明确本地缓存 / 分布式缓存 / CDN 三层职责与失效策略；**必须**定义缓存穿透（空值缓存或布隆过滤器）、击穿（互斥锁或逻辑过期）、雪崩（过期时间加随机抖动）三防 | 无失效策略的缓存；缓存与主数据不一致且无兜底 |
| 异步与消息队列 | 明确消息的投递语义（至少一次 / 最多一次 / 精确一次）、消费幂等、死信处理、积压告警阈值 | 用 MQ 做同步调用；无死信队列；消费失败静默吞掉 |
| 批处理与合并写 | 定义单批大小、最大等待时间、失败重试上限 | 无限攒批导致延迟不可控 |
| 读扩展 | 读多写少场景**应该**读写分离；**必须**处理主从延迟（读己之写场景走主库或会话粘滞） | 写完立刻读从库且无延迟处理 |
| 写扩展 | 单表预计 12 个月内超 **500 万行**或单库 QPS 超 **5000** 时，**必须**给出分库分表或归档方案（含分片键、路由、跨分片查询与事务的处理方式） | 无分片键设计就上分片中间件 |
| CDN / 边缘缓存 | 静态资源**必须**走 CDN；**必须**定义缓存键、TTL、刷新/预热机制 | 静态资源与 API 同源同域 |
| 限流与隔离 | 按调用方/租户/接口维度限流；不同租户的流量**禁止**共用无限队列（见 `resilience-and-ops.md`） | 全局单桶限流导致单租户拖垮全体 |

**必须**：上述任一手段引入后，**必须**在 `nfr-baseline.md` §六 的观测字段中补充对应指标（命中率、积压量、延迟、饱和）。

## 五、数据演进与多租户

### 5.1 数据演进

**必须**：

- schema 变更走**扩展-迁移-收缩**三步：先加新字段（双写）→ 回填历史数据 → 切换读取 → 观察一个发布周期 → 再删旧字段。**禁止**在同一次发布中「改名 + 迁移 + 删除」；
- 每次 schema 变更提供**可执行的回滚方案**（含数据回滚），并评估锁表时间与对在线流量的影响；
- 变更前输出书面方案并经用户确认（见 `AGENTS.md`「数据变更与 DDL 确认关卡」）。

### 5.2 多租户

**必须**明确租户隔离模型并写入设计文档：

| 模型 | 隔离强度 | 适用 | 必须处理 |
|---|---|---|---|
| 独立库/独立实例 | 强 | S 级、强合规要求 | 连接与资源配额管理 |
| 共享库 + 租户字段 | 中 | A/B 级常规 SaaS | **必须**在所有查询强制带租户条件（用统一守卫/拦截器，不依赖人工书写） |
| 混合 | 按需 | 大客户独立、小客户共享 | 迁移路径与数据搬移方案 |

**必须**：租户 ID 只能从可信身份派生，**禁止**从请求参数取；跨租户访问**必须**有结构性测试断言（遍历接口验证租户过滤存在），不能依赖人工检查。

## 六、云原生与弹性

**必须**（S/A 级）：

- 应用配置与镜像分离，同一镜像可在多环境部署（**禁止**为环境打不同镜像）；
- 启动就绪探针（readiness）与存活探针（liveness）语义分离：readiness 反映「能否接流量」（依赖就绪才置为 true），liveness 反映「是否需要重启」（**禁止**把下游依赖故障写进 liveness，否则会引发重启风暴）；
- 优雅停机：收到终止信号后停止接新流量、等待在途请求完成（默认宽限期 ≥ 30 s），超时再强制退出；
- 资源请求与上限（requests/limits）明确，**禁止**无上限部署；
- 弹性伸缩指标与阈值明确（CPU / QPS / 队列深度），含冷却时间与最小实例数（S 级最小实例数 ≥ 2）。

**应该**：基础设施即代码（IaC）管理部署拓扑；环境配置由唯一维护源生成或同步，**禁止**手工在多环境各改一遍（副本差异视为缺陷）。

## 验收标准

- [ ] 模块依赖图为 DAG，无循环依赖；分层职责在设计文档中标出
- [ ] 每个对外接口有机器可读契约，且契约与实现同源
- [ ] 版本载体已确定，兼容性判定表逐项检查并记录结论
- [ ] 旧版本下线有公告期与调用量归零证据（如涉及）
- [ ] 存在变化预期的维度已预留扩展点，核心流程无类型分支
- [ ] 所有配置项有默认值与缺失行为说明
- [ ] 采用的并发手段逐项说明理由与代价，配套观测指标已补齐
- [ ] 缓存三防（穿透/击穿/雪崩）已定义；MQ 投递语义、幂等与死信已定义
- [ ] schema 变更走三步演进，附可执行回滚方案
- [ ] 多租户隔离模型已明确，租户过滤有结构性测试断言
- [ ] S/A 级具备探针分离、优雅停机、资源限额、弹性伸缩

## 反例

| 反例 | 违反项 | 正确做法 |
|---|---|---|
| Controller 直接查库，无用例层 | §一 分层 | 分层调用，业务编排集中用例层 |
| 接口没有版本号，字段说改就改 | §2.2 版本策略 | 契约版本化，不兼容变更升版本 + 公告期 |
| 核心流程里 `if (channel == "wx") ... else if ...` | §三 扩展点 | 策略注册表，新增渠道只加文件 |
| 缓存永不过期，靠重启刷新 | §四 缓存 | 定义 TTL + 抖动 + 主动失效 |
| 先不分表，等慢了再说 | §四 写扩展 | 按 500 万行 / 5000 QPS 阈值给出分片方案 |
| 多租户查询靠开发者记得带 `tenant_id` | §5.2 多租户 | 统一守卫 + 结构性断言强制过滤 |
| liveness 探针里查数据库 | §六 探针 | readiness 查依赖，liveness 只判进程自身 |

## 检查清单

- [ ] 依赖方向单向，无循环依赖，无跨层直连
- [ ] 契约机器可读、与实现同源，错误码全集已定义
- [ ] 版本载体明确，不兼容变更已升版本并公告
- [ ] 扩展点已预留，配置有默认值
- [ ] 缓存三防 / MQ 语义 / 幂等 / 背压 / 限流维度均已定义
- [ ] 容量阈值（500 万行 / 5000 QPS）触及时有分片或归档方案
- [ ] schema 变更可回滚，多租户过滤有断言
- [ ] S/A 级探针分离、优雅停机、资源限额、弹性伸缩齐备
